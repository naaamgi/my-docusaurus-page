HTS 진단 가이드

Windows 데스크톱 HTS 클라이언트를 진단하는 순서를 단계별로 정리한 문서다. 각 단계에서 무엇을 확인하고, 어떤 명령을 쓰고, 어떤 결과를 증적으로 남기는지를 적었다. 명령은 CMD(명령 프롬프트)에서 바로 실행할 수 있는 것을 위주로 적었다.

대상과 전제
  • 대상: Windows에서 설치해 쓰는 HTS 클라이언트(EXE). 서버 측 점검은 이 문서의 범위가 아니다.
  • 진단 PC는 인터넷이 막힌 폐쇄망일 수 있다고 가정한다. 필요한 도구는 미리 반입한다.
  • 명령의 [ ]는 자기 환경에 맞게 바꿔 넣는 값이다.

진단 흐름 한눈에 보기​

단계하는 일주 도구
0준비: 범위, 계정, 도구, 증적 폴더-
1대상 파악: 설치 경로, 프로세스, 모듈, 보안 솔루션tasklist, frida-ps, Frida
2정적 분석: 파일, 문자열, 설정, 서명PowerShell, strings 계열, PE 도구
3통신 분석: 접속 대상, 프로토콜, 암호화 여부netstat, 패킷 캡처, frida-trace
4Frida 연결 확인: attach / spawnfrida, frida-ps
5동적 분석: 송수신 데이터, 암호화 API 후킹frida-trace, 직접 작성 스크립트
6메모리 평문 노출 점검fridump3
7로컬 저장 정보 점검: 파일, 로그, 레지스트리PowerShell, reg query
8클라이언트 측 검증 점검Frida
9정리: 증적, 취약점 기록-

0단계. 준비​

진단을 시작하기 전에 아래를 확인한다.

항목확인 내용
진단 범위대상 프로그램 이름, 버전, 점검 항목, 해도 되는 행위(후킹, 메모리 덤프, 변조 시도)
진단 계정모의 투자 또는 테스트 계정인지, 실제 주문이 나가는 계정인지
도구 반입Frida(frida + frida-tools), fridump3, 필요 시 패킷 캡처 도구.
실행 권한관리자 권한 CMD 사용 가능 여부 (권한이 높은 프로세스에는 일반 권한으로 붙을 수 없는 경우가 있다)
증적 폴더날짜와 단계별로 폴더를 미리 만든다
mkdir C:\work\evidence\01_target C:\work\evidence\03_network C:\work\evidence\05_hook C:\work\evidence\06_dump C:\work\evidence\07_local

증적 기본 원칙

  • 명령과 결과를 같이 남긴다. Frida는 -o 파일로 콘솔 출력을 저장하고, 일반 명령은 > 파일.txt로 저장한다.
  • 화면 캡처에는 시각과 PC 환경이 보이게 한다.
  • 실제 계정, 계좌번호, 토큰은 보고서에 쓸 때 마스킹한다.

1단계. 대상 파악​

HTS가 어떤 프로세스와 모듈로 구성되어 있는지 먼저 파악한다. 이후 모든 단계가 이 정보를 바탕으로 한다.

1-1. 설치 경로와 파일 확인​

HTS를 실행한 상태에서 프로세스의 실행 파일 경로를 확인한다.

frida -p [PID] -q -t 5 -e "console.log(Process.enumerateModules()[0].path)"
부분의미
-p [PID]이 PID의 프로세스에 attach
-q -t 5프롬프트 없이 실행하고 5초 뒤 종료
-e "..."JS 한 줄을 바로 실행
Process.enumerateModules()[0].path첫 번째 모듈(= 프로세스의 실행 파일)의 전체 경로

1-2. 프로세스 구성 확인​

HTS는 프로세스가 여러 개(메인, 시세, 보안 모듈, 업데이트 등)인 경우가 많다. 어떤 프로세스가 통신과 암호화를 하는지 PID로 구분해야 한다.

frida-ps
tasklist /v /fi "IMAGENAME eq [프로세스 이름].exe"
명령확인하는 것
frida-psFrida가 인식하는 전체 프로세스(PID, 이름)
tasklist /v /fi "IMAGENAME eq [이름].exe"해당 이름 프로세스의 상세 정보(창 제목, 사용자 등)

기록할 것: 프로세스 이름, PID, 부모 자식 관계(누가 누구를 띄웠는지), 어떤 프로세스가 로그인 화면과 주문 화면을 담당하는지.

1-3. 로드된 모듈 확인​

대상 프로세스에 로드된 DLL을 확인한다. 윈도우 폴더 밖의 DLL이 증권사 또는 보안 업체 모듈일 가능성이 높다.

frida -p [PID] -q -t 5 -e "Process.enumerateModules().forEach(function(m){ if (m.path.toLowerCase().indexOf('windows') < 0) console.log(m.name, m.path) })"
부분의미
Process.enumerateModules()로드된 모듈 목록(배열)
m.path.toLowerCase().indexOf('windows') < 0경로에 windows가 없는 모듈만 선택
console.log(m.name, m.path)모듈 이름과 경로 출력

이름만 빠르게 보려면 CMD 기본 명령을 쓴다.

tasklist /m /fi "PID eq [PID]"
부분의미
/m프로세스가 로드한 DLL 목록 표시
/fi "PID eq [PID]"이 PID만 필터링

1-4. 보안 솔루션 식별​

금융권 HTS는 보통 아래 보안 기능이 함께 동작한다. 이 기능들이 이후 단계(Frida 연결, 메모리 덤프)에 영향을 주므로 먼저 어떤 것이 있는지 알아 둔다.

보안 기능확인 방법이후 영향
키보드 보안로그인 창 입력 시 별도 드라이버/모듈 로드 여부, 서비스 목록입력값 캡처 점검
백신, 무결성 검사모듈 목록과 프로세스 이름에서 보안 업체 DLL 확인파일 변조, 후킹 탐지 가능
anti-debug, anti-hookingattach 시 프로세스 종료, 에러 여부(5단계)Frida 사용 가능 여부
통신 구간 암호화 모듈WS2_32, bcrypt, 자체 DLL 호출 관계(3, 5단계)후킹 지점 결정
sc query type= service state= all | findstr /i "[보안 업체 이름 일부]"
driverquery /v | findstr /i "[보안 업체 이름 일부]"
명령의미
sc query type= service state= all모든 서비스 목록 (type= 뒤에 공백이 필요하다)
driverquery /v로드된 드라이버 목록과 상세 정보
findstr /i대소문자 구분 없이 문자열로 거르기

1단계 증적: 프로세스 목록, 로드 모듈 목록, 보안 솔루션 식별 결과.

2단계. 정적 분석​

실행하지 않고 파일 자체에서 볼 수 있는 것을 확인한다.

2-1. 파일 목록과 해시​

dir "[HTS 설치 폴더]" /s /a-d /t:w > C:\work\evidence\01_target\files.txt
certutil -hashfile "[HTS 설치 폴더]\[실행 파일].exe" SHA256
부분의미
dir /s하위 폴더까지 모두 나열
/a-d폴더는 빼고 파일만 표시
/t:w마지막 수정 시각을 표시
> 파일결과를 파일로 저장
certutil -hashfile "파일" SHA256파일의 SHA256 해시. 진단 대상 버전을 특정하는 증적이 된다

2-2. 설정 파일, 로그, 설치 폴더 권한​

dir "[HTS 설치 폴더]" /s /b | findstr /i /l ".ini .xml .json .cfg .config .log .db"
icacls "[HTS 설치 폴더]"
명령확인하는 것
dir /s /b하위 폴더까지 파일 경로만 나열
findstr /i ".ini .xml ..."설정 및 로그 성격의 파일만 거르기 (공백으로 구분한 각 문자열 중 하나라도 맞으면 출력)
icacls폴더의 접근 권한. 일반 사용자에게 쓰기 권한이 있으면 DLL 교체 등의 위험이 있다

열어 볼 것: 서버 주소, 포트, 암호화 설정, 디버그 플래그, 계정 정보, 키 문자열이 평문으로 들어 있는지.

2-3. 문자열 검색​

실행 파일과 DLL에서 하드코딩된 값을 찾는다. Sysinternals strings가 있다면 아래처럼 쓴다.

strings -n 8 "[파일 경로]" > C:\work\evidence\01_target\strings_[파일 이름].txt
옵션의미
-n 88글자 이상인 문자열만 추출

찾을 것: 서버 주소(IP, 도메인), API 경로, 키나 시크릿으로 보이는 문자열, 테스트 계정, 디버그용 URL.

2-4. 디지털 서명​

sigcheck -nobanner -a "[파일 경로]"

Sysinternals sigcheck를 사용한다(반입 필요).

부분의미
-nobanner시작 배너를 출력하지 않음
-a서명 상태, 서명자, 버전 등 상세 정보 표시
결과의미
Verified: Signed서명이 유효
Unsigned서명이 없음 (프로그램 위변조 검증이 약할 수 있다)

도구가 없으면 파일 우클릭 → 속성 → 디지털 서명 탭에서 확인한다.

2단계 증적: 파일 해시, 설정 파일에서 발견한 민감 정보(마스킹), 폴더 권한, 서명 상태.

3단계. 통신 분석​

HTS가 어디에, 어떤 방식으로 통신하는지 파악한다.

3-1. 접속 대상 확인​

HTS를 실행하고 로그인한 뒤, 대상 프로세스의 연결을 확인한다.

netstat -ano | findstr "[PID]"
옵션의미
-a모든 연결과 대기 중인 포트
-n주소와 포트를 숫자로 표시 (이름 변환을 하지 않아 빠르다)
-o해당 연결을 소유한 PID를 함께 표시

기록할 것: 접속 IP, 포트, 연결 상태(ESTABLISHED), 프로토콜(TCP/UDP). 로그인 전후, 시세 조회, 주문 시점마다 접속 대상이 달라지는지 본다.

3-2. 프로토콜과 암호화 여부​

패킷 캡처 도구(Wireshark 등)로 해당 IP·포트의 통신을 캡처한다. 캡처 필터 예시는 다음과 같다.

host [서버 IP] and port [포트]
확인판단
TLS 핸드셰이크가 보인다표준 TLS. 인증서 검증, 프로토콜 버전, 암호 스위트를 점검
데이터가 읽히는 평문암호화되지 않은 통신 (계정, 주문 정보가 노출되면 취약)
읽을 수 없는 바이너리자체 암호화 또는 압축. 5단계에서 암호화 전 데이터를 후킹으로 확인

기록할 것: 암호화 여부, 프로토콜 이름(HTTP, TLS, 자체 규격), 로그인 요청에 계정 정보가 어떤 형태로 실리는지.

3-3. 송수신 함수 후킹으로 확인​

패킷 캡처만으로 부족하면 암호화되기 전 데이터를 Frida로 본다. 5단계에서 이어서 진행한다.

3단계 증적: netstat 결과, 패킷 캡처 파일, 프로토콜 판단 근거.

4단계. Frida 연결 확인​

Frida가 대상에 붙을 수 있는지부터 확인한다. 금융권 앱은 anti-debug, anti-hooking이 걸려 있어 붙는 순간 종료될 수 있다.

4-1. attach 시도​

frida -p [PID]
결과의미다음 행동
REPL 프롬프트가 뜬다 ([Local::PID::...]->)attach 성공4-2로 진행
프로세스가 종료된다보안 모듈이 탐지해서 종료했을 가능성4-3 spawn 시도, 기록
Failed to attach 에러권한 부족이거나 보호된 프로세스관리자 권한 CMD로 재시도

4-2. 동작 확인​

붙은 뒤에는 한 줄을 실행해서 스크립트가 정상 실행되는지 본다.

frida -p [PID] -q -t 5 -e "console.log(Process.arch, Process.enumerateModules().length)"

여기까지 되면 같은 프로세스에서 이후 후킹이 가능한 상태다.

4-3. spawn 시도​

attach가 막히면 프로그램을 Frida로 직접 실행한다.

frida -f "[HTS 실행 파일 경로]" --pause

--pause로 시작 지점에서 멈춘 상태로 REPL이 열린다. 필요한 후킹을 건 뒤 %resume을 입력한다.

옵션의미
-f "경로"이 프로그램을 Frida가 직접 실행(spawn)
--pause시작 지점에서 메인 스레드를 멈춘 채로 둔다. 후킹을 걸고 %resume으로 재개
--kill-on-exit(선택) Frida를 종료하면 실행한 프로그램도 종료

4-4. 연결이 안 될 때​

  • 프로세스가 여러 개이면 다른 PID(예: 보안 모듈이 아닌 메인 프로세스)로 시도한다.
  • attach 시점을 바꿔 본다(로그인 전, 로그인 후, 보안 모듈 로드 전후).
  • 이 환경에서 확인된 우회 방법은 실제 진단 기록으로 별도 정리할 내용이다. 허용된 범위에서만 시도하고, 무엇을 시도했고 어떤 결과였는지 모두 기록한다.

4단계 증적: attach 성공 여부 화면, 실패 시 에러와 프로세스 종료 시각.

5단계. 동적 분석: 송수신 데이터와 암호화 확인​

5-1. 호출되는 API 훑기​

먼저 frida-trace로 어떤 API가 호출되는지 본다. 로그인, 시세 조회, 주문처럼 하나의 동작만 하면서 로그를 본다.

frida-trace -p [PID] --decorate -i "WS2_32.dll!send*" -i "WS2_32.dll!recv*" -o C:\work\evidence\05_hook\net_trace.log
부분의미
-p [PID]대상 프로세스에 attach
--decorate로그에 모듈 이름 표시
-i "WS2_32.dll!send*"소켓 송신 함수(send, sendto)를 추적
-i "WS2_32.dll!recv*"수신 함수(recv, recvfrom)를 추적
-o 파일로그를 파일로 저장

WSASend, WSARecv도 함께 보려면 -i "WS2_32.dll!WSA*"를 추가한다. 패턴은 모듈!함수 형태이고 *는 와일드카드다. 패턴 끝에 /i를 붙이면 대소문자를 무시한다(5-2 참고).

5-2. 암호화 API 확인​

HTS가 윈도우 암호화 API를 쓰는지 본다.

frida-trace -p [PID] --decorate -i "bcrypt.dll!BCrypt*Crypt*" -i "CRYPT32.dll!Crypt*Crypt*" -o C:\work\evidence\05_hook\crypto_trace.log
결과판단
로그인, 주문 시 호출이 잡힌다윈도우 암호화 API 사용. 인자를 찍어 평문, 키, IV를 확인
아무것도 안 잡힌다자체 구현 암호화이거나 HTS 자체 DLL 내부 함수. 5-4의 offset 후킹으로 진행

대소문자를 구분하지 않고 넓게 훑으려면 -i "*crypt*/i"를 쓰되, 범위가 넓어 로그가 폭발할 수 있으므로 모듈을 지정해서 쓴다. 패턴 끝의 /i가 대소문자 무시이고, 없으면 대소문자를 구분한다(*enc*는 CryptEncrypt를 못 잡는다).

5-3. 인자와 반환값 직접 보기​

frida-trace가 자동 생성한 핸들러(__handlers__\모듈\함수.js)를 수정하면 인자를 읽을 수 있다. 예시로 send의 데이터를 16진수로 찍는다.

{
  onEnter(log, args, state) {
    const len = args[2].toInt32();            // send(socket, buf, len, flags)
    log('send len=' + len);
    log(hexdump(args[1], { length: Math.min(len, 64) }));  // 앞 64바이트만
  },
  onLeave(log, retval, state) {
  }
}
부분의미
args[1], args[2]send의 두 번째(버퍼), 세 번째(길이) 인자
hexdump(ptr, { length })메모리를 16진수와 문자로 보여준다
Math.min(len, 64)너무 긴 데이터는 앞부분만 출력

확인할 것

  • 로그인 시 비밀번호, 인증 정보가 암호화 전 평문으로 호출 인자에 있는가 (정상적인 구조에서도 암호화 API 직전에는 평문이 보이는 것이 일반적이므로, 문제는 암호화되지 않은 채 전송되는지, 키가 고정값인지, 약한 알고리즘인지이다)
  • 키와 IV가 호출마다 바뀌는가, 고정인가
  • 사용 알고리즘이 안전한가 (예: DES, RC4, ECB 모드는 취약)

5-4. HTS 자체 함수 후킹 (이름이 없는 경우)​

이름이 공개(export)되지 않은 내부 함수는 IDA나 Ghidra로 찾은 offset으로 후킹한다.

frida-trace -p [PID] --decorate -a "[모듈 이름]!0x[offset]" -o C:\work\evidence\05_hook\internal_trace.log

offset은 모듈 base 주소로부터의 거리다. IDA의 주소에서 이미지 base를 뺀 값을 쓴다. 어떤 함수가 많이 불리는지 단서가 필요하면 frida-discover -p [PID]를 쓴다.

5단계 증적: 호출 로그 파일, 평문 확인 화면, 사용 알고리즘과 키 정보(마스킹).

6단계. 메모리 평문 노출 점검​

HTS가 사용 중에 계정, 비밀번호, 토큰, 주문 정보를 메모리에 평문으로 남겨 두는지 확인한다.

6-1. 점검 시나리오 정하기​

메모리에는 그 시점에 있었던 데이터만 남는다. 아래처럼 시점을 정해서 각각 덤프한다.

시점확인할 값
로그인 직후아이디, 비밀번호, 인증서 비밀번호, 세션 토큰
로그아웃 직후위 값이 지워졌는지 (남아 있으면 취약)
주문 후주문 번호, 계좌번호, 수량, 가격

점검할 때는 검색에 쓸 알려진 값(테스트 계정의 아이디와 비밀번호)을 정해 두면 판단이 쉽다.

6-2. 메모리 덤프​

폴더를 먼저 만들고 덤프한다(fridump3는 존재하지 않는 폴더를 만들지 못하고 종료한다).

mkdir C:\work\evidence\06_dump\login
python fridump3.py -s -o C:\work\evidence\06_dump\login [PID]
옵션의미
-s덤프에서 문자열을 추출해 strings.txt로 저장
-o 폴더출력 폴더 (미리 만든 폴더)
[PID]대상 프로세스

기본값은 읽기·쓰기 영역(rw-)이다. 더 넓게 보려면 -r(읽기 전용 영역 포함, 데이터와 오류가 모두 늘어난다)을, 파일 하나의 최대 크기를 줄이려면 --max-size [바이트]를 추가한다.

6-3. 검색​

findstr /s /i /m "[검색할 문자열]" C:\work\evidence\06_dump\login\*
옵션의미
/s하위 폴더까지 검색
/i대소문자 구분 안 함
/m일치하는 파일 이름만 출력

findstr은 한글(UTF-16)이나 바이너리 안의 문자열을 놓칠 수 있다. 이때는 strings.txt에서 검색하거나, 16진수 검색이 되는 도구를 쓴다.

findstr /i /n "[검색할 문자열]" C:\work\evidence\06_dump\login\strings.txt

6-4. 판단​

결과판단
비밀번호가 평문으로 발견됨취약. 어떤 시점에 발견됐는지 기록
로그아웃 후에도 계정, 토큰이 남아 있음취약(사용 후 메모리 정리 미흡)
값이 발견되지 않음해당 시점, 해당 영역(rw-)에서는 미발견으로 기록 (다른 시점, 다른 영역에서 있을 수 있음)

6단계 증적: 덤프 명령, 검색 명령과 결과 화면, 발견된 값의 주변 문자열(마스킹), 덤프 시점.

7단계. 로컬 저장 정보 점검​

실행 중이거나 종료 후에 PC에 남는 정보를 확인한다.

7-1. 파일 변경 추적​

HTS를 사용하기 전 파일 목록을 남기고, 사용 후 달라진 파일을 비교한다.

dir "[HTS 설치 폴더]" "%APPDATA%" "%LOCALAPPDATA%" "%TEMP%" /s /a-d /t:w > C:\work\evidence\07_local\before.txt

HTS를 사용한 뒤 같은 명령을 after.txt로 저장하고 비교한다.

fc C:\work\evidence\07_local\before.txt C:\work\evidence\07_local\after.txt > C:\work\evidence\07_local\diff.txt
부분의미
"%APPDATA%" "%LOCALAPPDATA%" "%TEMP%"사용자 데이터, 로컬 데이터, 임시 폴더
/s /a-d /t:w하위 폴더 포함, 파일만, 수정 시각 표시
fc 파일1 파일2두 텍스트 파일의 다른 부분을 출력

실시간으로 보고 싶으면 Sysinternals Process Monitor에서 프로세스 이름으로 필터링한다(Process Name is [HTS 프로세스]).

7-2. 확인할 정보​

위치확인
로그 파일아이디, 계좌번호, 토큰, 주문 내용, 에러에 포함된 민감 정보
설정, 캐시 파일최근 접속 계정, 자동 로그인 정보, 저장된 비밀번호(평문 또는 쉽게 복호화되는 형태)
임시 폴더(%TEMP%)사용 후 지워지지 않은 임시 파일
레지스트리설정값, 저장된 계정
reg query "HKCU\Software\[HTS 제조사 또는 이름]" /s
옵션의미
reg query "키"레지스트리 키의 값을 조회
/s하위 키까지 모두 조회

7-3. 판단​

저장된 비밀번호나 토큰이 평문이거나 Base64 같은 단순 인코딩이면 취약이다. 파일 접근 권한도 함께 확인한다(2-2의 icacls).

7단계 증적: 변경된 파일 목록, 민감 정보가 있는 파일의 해당 부분(마스킹), 레지스트리 조회 결과.

8단계. 클라이언트 측 검증 점검​

HTS가 클라이언트에서만 검증하고 서버를 믿는 구조인지 확인한다. 이 단계는 반드시 허용된 범위와 테스트 계정으로만 진행한다.

8-1. 점검 항목​

항목방법취약 판단
프로그램 위변조 검증파일을 수정한 뒤 실행하거나, 무결성 검사 함수의 반환값을 관찰변조해도 정상 실행되고 접속된다
클라이언트 입력값 제한주문 수량, 가격 등을 화면에서 막은 값을 후킹으로 바꿔서 전송서버가 값을 검증하지 않고 처리한다
클라이언트 단독 인증, 권한 판단로그인 성공 여부, 권한 값을 반환하는 함수의 반환값 관찰클라이언트 반환값만으로 기능이 열린다

8-2. 반환값 관찰 및 변경​

Interceptor.attach(ptr('[함수 주소]'), {
  onEnter(args) { console.log('called'); },
  onLeave(retval) {
    console.log('original ret=' + retval.toInt32());
    // retval.replace(1);   // 변경이 허용된 테스트에서만
  }
});
부분의미
Interceptor.attach(주소, { onEnter, onLeave })주소의 함수 진입과 반환을 가로챈다
retval.toInt32()원래 반환값을 정수로 읽는다
retval.replace(값)반환값을 바꾼다 (주석 처리해 둔 이유: 관찰만으로 충분한지 먼저 판단)

함수 주소를 얻는 방법은 이름이 있으면 Process.getModuleByName('[모듈]').getExportByName('[함수]'), 없으면 Process.getModuleByName('[모듈]').base.add(0x[offset])이다(16/17 공통).

8단계 증적: 변조 전후 동작 비교 화면, 서버 응답.

9단계. 정리​

9-1. 증적 점검​

  • 단계별 폴더에 명령 로그, 결과 화면, 캡처 파일이 있는지 확인한다.
  • 실제 계정, 토큰은 마스킹본을 따로 만든다.
  • 진단 중 만든 파일(스크립트, 덤프)의 보관, 폐기 방침을 고객사 기준에 맞춘다. 메모리 덤프에는 민감 정보가 들어 있다.

9-2. 취약점 기록 틀​

항목내용
점검 항목예: 메모리 평문 노출
발견 위치프로세스, 모듈, 파일 경로, 시점
재현 절차단계별 명령과 조작 (처음부터 따라 하면 재현되도록)
증적로그 파일명, 화면 캡처
영향어떤 정보가 어떻게 노출되고 어떤 위협으로 이어지는지
조치 방안예: 사용 후 메모리 소거, 암호화 적용, 클라이언트 검증 보완

점검 체크리스트​

준비, 대상 파악​

  • 진단 범위, 계정, 허용 행위를 확인했다
  • 프로세스 구성(PID, 역할)을 기록했다
  • 로드 모듈과 보안 솔루션을 식별했다

정적, 통신​

  • 설치 폴더 권한, 설정 파일의 민감 정보를 확인했다
  • 서명 상태를 확인했다
  • 접속 IP, 포트, 암호화 여부를 확인했다

동적​

  • Frida attach(또는 spawn) 가능 여부를 기록했다
  • 송수신, 암호화 API를 추적했다
  • 암호 알고리즘, 키 관리 방식을 확인했다

메모리, 로컬​

  • 로그인 직후, 로그아웃 직후, 주문 후 시점별 덤프를 점검했다
  • 로그, 설정, 임시 파일, 레지스트리를 점검했다

클라이언트 검증​

  • 위변조 검증, 입력값 검증, 권한 판단을 점검했다

마무리​

  • 증적을 정리하고 민감 정보를 마스킹했다
  • 취약점 기록 틀에 맞춰 작성했다
