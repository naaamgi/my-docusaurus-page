파라미터 변조와 인가 우회

1. 정보 수집 방법​

파라미터 변조의 핵심은 "어디에 뭘 넣을 수 있는가"를 파악하는 것.

방법찾을 수 있는 것
소스코드 보기 (Ctrl+U)주석, 숨겨진 링크, 사용하지 않는 함수
개발자 도구 (Elements)hidden 필드, name 속성, disabled 속성
URL 패턴 유추/qna/write → /notice/write, /admin
불필요한 파일 존재.bak, .old, .txt → 백엔드 소스코드 노출

2. 인증 vs 인가​

구분설명
인증 (Authentication)누구인지 확인
인가 (Authorization)무엇을 할 수 있는지 확인

핵심: 프론트엔드에서 버튼을 숨기는 것은 UX 처리일 뿐. 백엔드에서 세션의 권한을 확인하지 않으면 URL 직접 입력으로 접근 가능.

3. 프로세스 검증 누락​

비밀번호 찾기 같은 다단계 절차에서 중간 단계를 건너뛰어도 최종 단계가 실행되면 취약.

흐름단계
정상 흐름1단계 인증 → 2단계 검증 → 3단계 변경
공격 흐름3단계 직접 요청 → 변경 성공

대응: 각 단계마다 세션에 이전 단계 통과 여부 저장.

4. 비밀글 읽기​

게시판에서 비밀글의 클릭을 프론트엔드에서만 막아놓은 경우, URL 직접 입력으로 접근.

# 예시
https://target.com/board/view?id=123&secret=1
# id 값을 직접 변경하여 다른 비밀글 접근 시도
https://target.com/board/view?id=124

5. 관리자 페이지 URL 유추​

/admin
/manager
/administrator
/admin/login
/notice/write
/board/admin
/manage
/cms

6. 응답 변조​

프론트엔드에서 로그인 성공/실패를 분기하는 경우, Burp Suite Intercept로 응답을 변조하여 우회.

// 원래 응답
{"result": "fail", "msg": "비밀번호가 틀렸습니다"}

// 변조 후
{"result": "success", "msg": "로그인 성공"}

핵심: 응답 변조 자체가 취약점이 아니라, 백엔드에서 세션 검증을 하지 않는 것이 취약점.

7. 쇼핑몰 금액 변조 공격​

7.1 Integer Overflow​

상품 개수를 극단적으로 큰 값으로 입력 → 총 금액이 음수로 전환.

quantity=9999999999999999

7.2 배송비 음수​

shipmentfee=-2759900
# 총액 = 상품가 + (-2759900) = 100원

7.3 포인트 조작​

usepoint=9999999
# 보유 포인트보다 큰 값을 입력

7.4 totalprice 직접 조작​

totalprice=100
# 결제 단계에서 totalprice 파라미터를 100으로 변경

7.5 없는 파라미터 삽입​

서버 코드에 setpoint 파라미터 처리 로직이 있지만 프론트에는 없는 경우, 직접 추가.

POST /order/complete
...
setpoint=99999&totalprice=100

7.6 HTML 변조 방법​

개발자 도구 → Elements → 대상 요소 우클릭 → Edit as HTML
- readonly 속성 삭제
- name 속성 변경
- hidden value 수정
- disabled 속성 삭제

7.7 대응 방안​

  • 사용자 입력값으로 금액을 결정하지 않는다
  • 서버에서 DB 조회 → 단가 × 수량으로 직접 계산
  • 음수 검증, 범위 검증 필수
  • 결제 금액은 세션 또는 서버 DB에서 관리

8. JavaScript 분석 기법​

8.1 실행 시점 이해​

HTML은 위에서 아래로 파싱. <script> 위치에 따라 DOM이 준비되지 않아 에러 발생 가능.

<!-- 잘못된 위치: DOM 로드 전 접근 시 에러 -->
<script>document.getElementById('btn').onclick = ...</script>
<button id="btn">클릭</button>

<!-- 올바른 위치: DOM 로드 후 실행 -->
<button id="btn">클릭</button>
<script>document.getElementById('btn').onclick = ...</script>

8.2 분석 도구​

도구사용법
이벤트 리스너 브레이크포인트Sources → Event Listener Breakpoints → Click
전체 파일 검색Ctrl + Shift + F
콘솔에서 함수 직접 호출checkPassword('test123')
요소 ID/Name에서 힌트 얻기Elements → id, name 속성 확인

9. strcmp 취약점 (PHP)​

PHP에서 strcmp(문자열, 배열) → NULL 반환, 느슨한 비교(==)에서 NULL == 0 → true.

# 공격 페이로드
login_pwd[]=anything

# 취약한 코드
if (strcmp($_POST['password'], $stored_hash) == 0) {
    // 로그인 성공 → strcmp 반환값이 NULL이고 NULL == 0 이므로 통과
}

# 대응: 엄격한 비교(===) 사용
if (strcmp($_POST['password'], $stored_hash) === 0) {

10. E2E 암호화 우회​

E2E 암호화는 전송 구간을 보호하지만, 암호화 전 데이터 조작을 막지 못함.

// Match & Replace로 암호화 함수 호출 직전에 prompt 삽입
// 원본 코드
var data = { amount: document.getElementById('price').value };
sendEncrypted(data);

// 변조 후: 암호화 전 데이터 조작
var data = { amount: prompt('금액 변조:', document.getElementById('price').value) };
sendEncrypted(data);

대응:

  • 서버에서 복호화 후 반드시 재검증
  • 서버에서 금액 직접 계산

11. 핵심 원칙 정리​

  1. 프론트엔드 검증은 UX용, 백엔드 검증이 진짜 보안
  2. 사용자 입력값을 절대 신뢰하지 않는다
  3. 금액 관련은 서버에서만 계산/결정
  4. 모든 단계마다 인증/인가를 검증
  5. 암호화 키는 서버에 보관
  6. 불필요한 파일/기능은 제거
  7. 에러 메시지에 민감 정보를 노출하지 않는다
  8. 파라미터 변조는 결국 인증/인가 취약점

트러블슈팅 체크리스트​

  • 모든 상태 변경 요청에 서버 측 인가 검증이 있는가?
  • 금액/포인트/수량이 서버에서 재계산되는가?
  • 다단계 프로세스에서 각 단계 검증이 이루어지는가?
  • 관리자 페이지에 접근 제어가 적용되어 있는가?
  • hidden 필드, disabled 속성에 의존하지 않는가?
